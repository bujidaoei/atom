# 项目开发与交付铁律

以下规则适用于本项目的全部开发、修改、重构、测试与发布工作。执行过程中必须严格遵守，不得自行省略、降低标准或扩大产品范围。

## 一、项目目标与边界

本项目的目标是：以官方 QoderWake 为产品参照，以 Pi 官方源码为唯一 Agent 内核，持续实现网页端及 Windows、macOS、Linux 桌面端的产品还原。
除以下明确允许的差异外，官方 QoderWake 登录后的全部界面、功能和交互均须按 1:1 标准还原：

1. **身份验证**：本项目仅使用 API Key 登录和身份验证，不接入、不研究、不复刻官方账号体系及登录流程。
2. **模型与调用链路**：本项目使用已接入的自有 AI 网关，官方模型列表须替换为网关提供的模型列表；忽略官方模型选用及计费逻辑。
3. **Agent 内核与技术实现**：本项目统一使用 Pi 官方 Agent 内核，并结合自有网关完成集成。模型调用、网关接入和任务调度的具体实现必须遵循本项目架构，不得照搬与该架构冲突的官方内部方案。
   上述差异仅限于必要范围，不得借此重新设计、简化或改变其余登录后的产品体验。任务执行、状态变化和结果反馈等用户可感知行为，仍应与官方保持一致。
   不得新增与官方 QoderWake 无关的功能、页面或业务流程。

## 三、Pi 复用与 Agent Runtime 开发顺序

Pi 官方源码是本项目唯一的 Agent 内核。凡涉及 Agent 或 Agent Runtime 的需求，必须严格按以下顺序执行。

### 1. 先核查当前源码

深入检查 `D:\bugu\_self\workdude\pi` 中的实际源码，确认需求是否已由以下能力支持：

- 官方现有实现；
- 官方公开接口与组件；
- 官方组件组合方式；
- 官方扩展机制。

若已支持，必须直接复用，不得重复实现，不得另建内核替代 Pi。
复用应充分且与项目需求相关，不得为扩大使用范围而引入无关能力。

### 2. 当前版本不支持时，先核查并更新官方稳定版

只有确认当前源码无法满足需求后，才进入官方稳定版更新流程，不得直接自行实现。
官方仓库：
[https://github.com/earendil-works/pi](https://github.com/earendil-works/pi)
更新要求：

- 以官方发布的最新正式稳定版本为准，不得擅自使用预发布版本或默认分支的最新提交。
- 更新前检查并妥善备份本地改动及必要文件，备份必须存放在 Pi 目录之外。
- 获取对应版本的完整源码，并整体替换旧源码，不得只复制部分文件、选择性合并或保留旧版本残留。
- 更新后核验目录内容与该官方稳定版本完整源码一致。
- 记录版本号、对应提交及更新日期。
- 若当前目录已与官方最新稳定版一致，只需记录核验结果，无须重复替换。
- 若无法可靠确认最新稳定版本或完成完整性核验，应如实说明阻碍，不得擅自改用其他版本。

### 3. 更新后重新核查并优先复用

重新检查最新版源码。若官方能力、组件组合或扩展机制已能满足需求，必须采用官方实现，并完成项目集成及必要的兼容性验证。

### 4. 官方仍不支持时，才允许最小补充

只有确认官方最新稳定版仍无法满足需求，才允许在 Pi 目录之外实现最小必要补充。
补充代码不得演变为独立 Agent 内核，不得修改、替代或重复实现 Pi 已有核心能力。
每项补充必须在代码及项目文档中明确记录：

- 具体需求与官方能力缺口；
- 已核查的 Pi 版本、相关源码位置及判断依据；
- 补充实现的位置、范围及与 Pi 的集成方式；
- 后续迁移条件：官方稳定版支持该能力后，必须迁移至官方实现，并完成补充代码的清理、重构和验证。

## 五、还原标准

在第一条明确的差异范围之外，以下内容均须以官方产品的实际表现为准：

1. **视觉一致**：页面结构、布局、尺寸、间距、字体、颜色、图标、动效及响应式表现达到像素级还原目标。
2. **交互一致**：点击反馈、输入行为、页面跳转、操作顺序、加载状态、异常处理及边界行为保持一致。
3. **功能一致**：登录后的功能完整可用，不得以占位页面、静态演示或简化流程代替真实实现。
4. **运行行为一致**：数据流转、状态变化、任务生命周期、文件处理、命令执行和结果展示，应在本项目 Pi 与自有网关架构下实现与官方一致的可观察行为。

不得自行省略功能、改变流程或重新设计官方体验。涉及技术架构差异时，应在保留产品行为的前提下完成适配。

## 六、先检查已有实现，避免重复开发

每次开发前，先检查项目当前代码与实际运行结果，明确：

- 已完整实现的部分；
- 已实现但存在差异或缺陷的部分；
- 尚未实现的部分。

已正确实现的内容不得重复开发。优先推进尚未完成的能力及已确认的差异，避免无实质进展的重复劳动。

## 七、按全新首版标准重构与清理

项目尚未上线，应按全新首版设计，不为历史版本保留无必要的兼容逻辑、过渡接口或兼容层。
允许并鼓励基于实际需要进行合理重构，但必须先确认用途、依赖及影响范围，再清理：

- 无用代码与重复逻辑；
- 废弃配置与无效依赖；
- 已被替代的实现；
- 不必要的抽象与历史兼容层。

重构应服务于功能完整性、架构清晰度和长期可维护性，不得偏离官方产品还原目标。

## 八、坚持生产级工程标准

所有实现必须符合生产级工程要求，不得以临时补丁、硬编码绕过或掩盖症状的方式替代正式设计。
具体要求：

- 从根因定位并解决问题，分析影响范围。
- 保持职责单一、高内聚、低耦合，明确模块边界与接口契约。
- 避免重复实现、循环依赖及过度设计。
- 兼顾可读性、可维护性、稳定性、安全性和性能。
- 完整处理必要的加载、错误、取消及资源释放行为。
- 改动后完成与风险相匹配的验证，确保结果可复现、可操作、可审查。

验证范围应与改动风险相匹配。相关检查通过后，除非出现新改动、新失败或未解决风险，否则不要无意义地重复验证。
