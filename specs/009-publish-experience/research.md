# Research: publication and checks
Reviewed 2026-10-02; official documentation research delegated per speckit-plan Phase 0. No competitor authenticated deployment was performed.

## Observed defect
Target application log: POST /api/projects/<id>/acceptance HTTP500, serialize.py:117, TypeError: cannot compare offset-naive and offset-aware datetimes. SQLAlchemy sessions retain committed objects; SQLite reloads UTC timestamps without tzinfo. Comparing a newly inserted aware check time with a reloaded naive generation time fails. Fix timestamp semantics explicitly and cover fresh/loaded objects, stale results and API save/reload.

## Decisions and alternatives
1. Default functional checks are advisory. Reject the current universal passing-evidence gate for ordinary publication; preserve explicit strict enterprise policy.
2. Reuse immutable artifact/revision and publication infrastructure. Do not re-enable mutable-workspace copying or manufacture verification reports.
3. Main interface is current online version plus chronological published snapshots, preview and restore. Keep draft unchanged on live restoration. Diagnostic IDs are disclosure-only.
4. Distinctive product value: explain each publication through content/version, check state and recoverability without forcing internal machinery onto the creator. Not a claim of novelty over all competitors.
5. Normalize existing UTC timestamps at serialization boundaries; do not migrate stored timestamp values for the check defect.
6. Public content requires an independently configured site and real ingress acceptance. Production currently has only IP console ingress; domain availability is requested while independent implementation proceeds. Do not improvise a shared-cookie publication origin.

## Existing architecture constraints
Production remains schema10, legacy sessions; verified publication requires later schema, durable sessions, content host and verifier. Existing release schema requires non-null verification and a passing-evidence trigger. Therefore direct publication needs a deliberate versioned policy/schema change, not removing a frontend disabled attribute. Existing original-checkout release history work remains untouched.

# IP-only publishing constraint (2026-10-02)

The owner has no domain and requests use of the server IP. Official references: [Let's Encrypt IP certificates](https://letsencrypt.org/2026/01/15/6day-and-ip-general-availability) are generally available but require automated six-day renewal; [MDN same-origin policy](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Same-origin_policy) isolates different ports for scripts and Web Storage; [RFC 6265 section 8.5](https://www.rfc-editor.org/rfc/rfc6265#section-8.5) explicitly says cookies do **not** isolate by port and warns against mutually distrusting services on different ports using security-sensitive cookies. Thus one IP with a separate publication port is not equivalent to a dedicated content host for arbitrary generated JavaScript. Paths also share origin/storage. A safe enterprise public browser cutover needs a separate hostname/site or a different authentication architecture plus per-project browser-origin design; an IP certificate alone does not solve the host or cross-project isolation. Do not silently enable untrusted public pages on the console IP. Revisit ingress after concrete safe isolation is designed and browser-tested.

Candidate for IP-only research, **not accepted**: The [CSP `sandbox` directive](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/sandbox) without `allow-same-origin` gives generated script an opaque origin even on direct navigation; `allow-scripts` permits JavaScript while denying its direct access to console cookies and Web Storage. The [W3C CSP specification](https://www.w3.org/TR/CSP2/#directive-sandbox) says header-enforced sandboxing applies beyond embedded frames. A trusted outer shell might scope an explicit state bridge by project and emulate only required localStorage calls while keeping user code in an opaque-origin iframe. This needs a threat-model and actual Chromium/Firefox/WebKit tests for direct URLs, relative ES modules, navigation, cookie writes, postMessage source validation, cross-project state, refresh durability and accessibility. Do not ship a polyfill or claim equivalence to native localStorage before those tests. If functionality or isolation cannot be proven, require a separately owned content hostname.

Feasibility update: MDN explicitly states that opaque-origin sandboxed resources cannot access `localStorage`, `document.cookie` and some other Web APIs; its [same-origin guidance](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Same-origin_policy) also identifies IndexedDB, BroadcastChannel and SharedWorker as affected. Therefore the CSP candidate cannot preserve the generated app's native synchronous localStorage behavior. A postMessage state bridge would be a different API and cannot faithfully replace synchronous reads, so it is rejected for this release. Distinct ports do create distinct Web Storage origins, but [RFC 6265 section 8.5](https://www.rfc-editor.org/rfc/rfc6265#section-8.5) confirms host cookies cross ports. A defensible IP-only route would require a cookie-free console credential transport **or** a separately verified console-origin proof in addition to its HttpOnly cookie, stable dedicated HTTPS origins for each project's preview and public page, bounded non-reusable port allocation and ingress lifecycle, cross-origin/CSRF protections, plus real browser and rollback tests. The candidate is specified in `ip-only-design.md`; no existing IP-only implementation meets FR-010 yet. Private COS storage does not change these browser boundaries.

Production ingress inspection: the existing Caddy v2.11.4 instance serves the console at the requested IP on HTTPS 443 with a Let's Encrypt short-lived IP certificate. Caddy currently publishes only port 443; a separate nginx container owns port 80 and relays its ACME challenge path to Caddy. No per-project content ports are live. The site configuration routes `/atom/*` to the API. [Docker Compose](https://docs.docker.com/reference/compose-file/services/) can publish a bounded port range, but an isolated `caddy:2` `caddy adapt` check rejected `https://159.75.231.98:40000-40002` with `invalid port`: a Caddyfile site address cannot use that range as one site. Explicit per-port addresses succeeded. Later isolated target drills copied the current certificate store and used the actual ACME route renderer/controller to certificate-verify first two and then **all 72** copied project identities on host-loopback ports, including same-digest reconciliation after Caddy restart; production listener replacement and external reachability are still unproven. [Let's Encrypt's current profiles](https://letsencrypt.org/docs/profiles/) list IP identifiers only under `shortlived` with 160-hour validity; the target's trusted IP certificate observed on 2026-10-03 expires 2026-10-08T00:03:39Z, so the existing port-80 challenge relay and automatic renewal are continuing delivery requirements. A project requires one stable HTTPS port to retain native Web Storage across releases, a durable port-to-binding ledger, and a fail-closed ingress/controller reconciliation. As [MDN notes](https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch), cross-origin simple requests can be sent with credentials before CORS blocks reading the response, so every cookie-authenticated write must verify the exact console origin server-side. The first guard increment is implemented in `console_auth.py` and `deps.py`; external ingress and production browser tests remain open.

Target deployment proxy finding: the current `atom-tls` container is on the existing application bridge at `172.19.0.2`, while another bridge peer is `172.19.0.3`. [Uvicorn's official settings](https://www.uvicorn.org/settings/) say forwarded protocol metadata is trusted only from configured connecting IPs; its default is loopback, so the Caddy bridge source must be pinned explicitly. [Caddy's reverse proxy documentation](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy#defaults) says it sets `X-Forwarded-Proto` and ignores incoming `X-Forwarded-*` values by default, preventing client-supplied header spoofing. A target rehearsal with the exact candidate image returned the correct preview/public identity from Caddy and 404 from the other bridge peer even when it supplied `X-Forwarded-Proto: https`. The existing nginx port-80 proxy relays ACME HTTP challenges to `atom-tls:80`; preserving that relay and the Caddy certificate volumes is part of the protected Caddy replacement. This is internal-proxy evidence, not external TLS validation.

Cookie-hardening limit: [MDN's browser compatibility data](https://github.com/mdn/browser-compat-data/blob/main/http/headers/Set-Cookie.json) records `__Host-Http-` enforcement in Chrome 140+ and Firefox 143+, but **not Safari**. Do not claim this prefix alone prevents generated script from setting a conflicting same-host cookie across supported browsers. The server has no globally routed IPv6 address at inspection, so separate IPv6 hosts are unavailable. A cookie-free console credential transport, or an independently required console-origin proof with a browser-tested threat model, must be implemented before an IP-only public release is accepted.

Preview exchange browser compatibility (2026-10-03): Firefox 146 sent `Origin: null` for the one-use preview POST while the trusted exchange document had `Referrer-Policy: no-referrer` and its fetch explicitly used `mode: 'same-origin'`; the server correctly rejected it with 403. [MDN's Referrer-Policy reference](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Referrer-Policy#effect_on_the_origin_header) documents that non-CORS same-origin-mode POSTs under `no-referrer` may carry `Origin: null`, whereas CORS-mode fetch sends the real origin. The exchange now uses `mode: 'cors'` for its relative same-origin URL, retaining `credentials: 'same-origin'`, `redirect: 'error'`, the strict server Origin check and no-referrer policy. This was found by real browser testing, not inferred from Chromium alone. Local Chromium/Firefox workspace preview passes; separate direct-TLS Chromium/Firefox/WebKit console and public-port tests cover proof, cookie planting, read/write denial and logout. Target ingress and owner browser acceptance remain open.

## Snapshot restoration versus schema rollback (2026-10-03)

[Vercel's official Instant Rollback guidance](https://vercel.com/docs/instant-rollback) treats deployment rollback as routing to a previous build and explicitly calls out changed behavior of external databases, APIs and CMSes. [Prisma's official recovery guidance](https://www.prisma.io/docs/orm/migrations/rollbacks-and-recovery) treats an already-applied schema rollback as a new migration, preserving history and warning about destructive data changes. Applied to Atom: owner-facing restore should move an immutable publication pointer within the current schema, keeping later drafts and history; it must not restore an old server database. The protected old-container rollback proven on 2026-10-03 was safe only because the old and candidate business tables still matched before the exercise. If later candidate writes exist, switching back to the preserved schema10 database would hide them. FR-014 therefore requires a machine-verified no-new-write gate or an explicit data-reconciling forward recovery; a warning or operator assertion alone is insufficient evidence.

Target evidence narrows the gate design: a consistent SQLite backup made immediately before the live recovery and the stopped candidate's later database had **different file SHA-256 values**, yet sorted-row comparisons across every application table found no changed logical rows. SQLite page layout/WAL checkpoint effects therefore make raw database-file hashes too strict even in a clean rollback. The read-only `deploy/candidate_write_fence.py` utility hashes schema and typed rows plus a bounded non-database file inventory; it must still be integrated with writer exclusion and a refusal path before FR-014 can be accepted.

The preserved old Caddy configuration routes the console by Docker name `atom-candidate:80`. During the currently deployed forward transaction, the old API is stopped and renamed, then the new candidate reuses `atom-candidate` **before** the old Caddy is replaced. That creates a brief interval in which the still-running old ingress can route user requests to the new schema18 API. A safe activation baseline cannot assume that no candidate writes occurred merely because the replacement Caddy has not started. The future write-fence transaction must keep old ingress from exposing that alias or close the candidate write path until the baseline and legacy import are reconciled; otherwise even an accurate later fingerprint could bless already-unmerged writes.

## Forward recovery after a refused rollback (2026-10-03)

Source audit found no schema18 forward-deployment transaction. `deploy/ip_cutover_apply.py` prepares a candidate specifically by migrating the protected schema10 source to schema18 and refuses a reused candidate directory. `deploy/image_only_cutover.sh` targets an older single-box schema10 data path and asserts schema10/3 after switching images; its protected preflight would reject the current schema18 candidate. Neither path may be repurposed after a real owner write. The installed rollback fence correctly resumes the current candidate instead of exposing stale schema10 data, but future image upgrades still need a separate current-generation source, fresh paired backup and compatibility/ingress gates. Decision: specify FR-016 and an explicit forward transaction from the active candidate; reject in-place image replacement and stale schema10 replay. This is a code/design finding, not a completed recovery capability.

## Caddy connection draining during publication maintenance (2026-10-03)

[Caddy's official global-options documentation](https://caddyserver.com/docs/caddyfile/options#grace-period) says the default HTTP-server grace period is eternal: during a config change, existing connections may remain on the retiring server indefinitely unless a finite `grace_period` is configured. The owner Chrome session reproduced the practical consequence after Atom's real forward-fault recovery: fresh strict-TLS probes saw normal routes, while its persistent HTTP/2 connection still received the old 503 maintenance body. Atom now requires a five-second bound on both source and maintenance Caddy bases before the next forward transaction, and the current production source was migrated under the host lock. A fresh probe remains necessary but cannot alone establish that all existing sessions have drained.
# Durable-proof project stream regression (2026-10-03)

In the signed-in production Chrome project, the stream badge stayed at “连接中断，点击重连” after reload. Chrome network events showed repeated HTTP 401 responses from `/atom/api/projects/{id}/events` while project and publication API calls succeeded. `useProjectStream.ts` used native `EventSource` with credentials, but the mandatory durable-console proof lives in `X-Atom-Console-Proof`; the server rejected the cookie-only stream as designed. The [WHATWG HTML Standard](https://html.spec.whatwg.org/multipage/server-sent-events.html) defines only `withCredentials` in `EventSourceInit`, with no caller-supplied request headers. The correction is an authenticated same-origin `fetch` stream that preserves the proof check, not a proof bypass or a token in the URL. Target TLS browser and live owner acceptance remain separate gates.
