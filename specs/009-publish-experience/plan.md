# Implementation Plan: Publish snapshots and optional functional checks
**Branch**: codex/009-publish-experience | **Date**: 2026-10-02 | **Spec**: spec.md

## Summary
Repair UTC check-result serialization first. Evolve immutable releases to explicit advisory versus required functional-check policy, then present publications as restorable snapshots. Preserve the existing Atom runtime and artifact isolation. Deployment must include configured independent content ingress, protected migration and actual recovery evidence.

## Technical Context
Python 3.12+/FastAPI/SQLAlchemy/SQLite backend, TypeScript/React/Vite frontend, pytest and actual Chromium acceptance; Linux Docker target. Existing revision ledger, ArtifactStore and release/content repositories remain the source of authority. Bounded storage reads and write-lock lifetimes follow existing infrastructure; publication does not invoke a model or regenerate content. Scope is generated static websites. No performance or high-availability claims without measured evidence.

## Constitution Check
PASS for staged implementation: preserve locked runtime/pi, existing user work, credentials and production data. Spec and tasks precede edits. Tests, frontend build, runtime integration, fault injection and live model/browser evidence are separate gates. Release migration/ingress acceptance remain required, not inferred from unit tests.

## Design
US1 normalizes UTC values before comparing or emitting acceptance timestamps; results remain honest and stale evidence remains hidden. Broader version-bound checks are tracked separately.
US2 reuses immutable registered artifacts and content policy checks. Introduce a schema version that represents advisory publication without forged verification identities, preserves existing verified release rows and enables strict policy explicitly. Preflight exact content outside the write lock, then repeat owner/head/generation checks inside the transaction. Persist idempotent receipts and audit transitions.
US3 list retained publications newest first with bounded pagination, timestamps, current-live marker and optional check details. Restore creates a new publication event from retained exact content, preserves draft head and uses expected generation to reject races. Historical preview remains owner-authorized unless deliberately published.
Content delivery reuses independent-site binding and host-only console sessions. The owner has no domain and requests IP-only access. Although IP TLS certificates now exist, different ports do not isolate cookies and one port for all projects would share browser storage. A safe IP-only design requires further work; no production activation until its cross-project and console isolation, migration and rollback tests pass. The private COS bucket supplies bytes, not an isolated browser origin.

The first IP-only security increment enforces the configured HTTPS console host on every durable cookie-authenticated API request and the exact console `Origin` on all unsafe methods, including ordinary project/settings routes that previously relied on a valid cookie alone. This closes one cross-port CSRF path; it does not isolate cookie namespace, supply per-project ports or constitute a public ingress design. ## Testing strategy amendment (owner direction, 2026-10-03)
The `a5f1793` production attempt exposed an ordering constraint: `app.legacy_publications` intentionally verifies the project's real preview/public HTTPS routes before committing the migrated release. It then atomically switches Caddy's base configuration to the normal console route, reconciles/probes again and records the final digest. If promotion fails after console exposure, the baseline-backed rollback gate decides between old-container restoration and retaining the candidate. Target Caddy/TLS denial and readiness checks and a real forward activation passed. An isolated real-Caddy post-promotion probe fault restored write-blocked maintenance ingress, but full paired production fault recovery and owner acceptance remain unproven.

## Forward-recovery design after a refused old-schema rollback (open)

`ip_forward_journal.ForwardJournal` adds ordered, fsynced intent/result phases bound to the root-private exact identity receipt. Captured backup paths and digests must match that identity. It refuses phase skips and requires an unchanged-write-fence claim before recording source restore after attempted exposure. The host-locked transaction must make that claim only after quiescing successor writers and comparing the logical baseline; the journal alone cannot execute recovery.
The candidate-ready event now requires six successor IDs disjoint from the source, exact successor image/directory and baseline/Caddy digests. This receipt is reserved for a handoff implementation that verifies each live service and strict-TLS maintenance; it cannot be inferred from a Compose exit code.
`ip_forward_stage.stage_locked` now composes the journal and existing current-generation, ingress, writer and capture components for the pre-handoff portion. It is deliberately internal until the remaining candidate replacement and crash/post-exposure recovery paths can consume its returned receipt under the same host lock. Ordinary exceptions attempt exact source restart, normal TLS ingress and full source reinspection before recording recovery. A caller losing the host lock before handoff would break the protocol; the final command must own that lock for the entire operation.
`ip_forward_identity.capture` seals four pinned bridge IPs from exact live API/preview/public/Caddy identities, rejects collisions and ties them to the same durable six-ID receipt before writer stop. `ip_forward_candidate.prepare` then verifies both paired manifests and unchanged schema18 release/origin state, confirms stopped source writer IDs and the still-running Caddy ID/IP, and builds private candidate inputs from those sealed addresses. Stopped Docker containers can lose their visible `IPAddress`; the first-cutover staging template's old Caddy address is also not authoritative. The target currently runs Caddy at `172.19.0.4` while the inactive template says `172.19.0.2`, a discrepancy caught by read-only production inspection. The preparation is offline; any normal failure can return to the exact source IDs through the still-held host lock. It does not yet replace or expose candidate containers.
`ip_forward_hold.hold` now records candidate intent, stops Caddy by exact ID and renames the six stopped source IDs to reserved held names. Its pre-exposure exception path restores those IDs and current ingress after partial stop/rename effects. This is still internal to the same host-locked transaction; candidate service startup and crash recovery must be ready before exposing a deploy command.
`ip_forward_start.start` uses a distinct Compose project for preview/public/verifier/Caddy, manually creates the network-sharing API/broker pair, checks exact image/binds/pinned addresses/ports and health, verifies all TLS maintenance routes, then writes the existing logical baseline before `candidate_ready`. It can remove only verified successor containers on an ordinary failure before source restoration. This stage remains internal until power-loss recovery and post-exposure write fencing are implemented and isolated real-service drills pass.

The post-exposure decision reads the root-private baseline only when its revision, image, candidate directory and digest match the phase journal. After TLS maintenance and exact successor writer exclusion, a fresh logical fingerprint may authorize source restoration only if unchanged. A changed fingerprint retains the new schema18 generation and its committed owner work. The strict baseline reader and real SQLite write-detection test are implemented; the host-locked decision and crash recovery are still pending.

`ip_forward_exposure.expose` is the internal same-lock promotion phase. It verifies six successor and six held source IDs, the sealed baseline and origin ledger, writes `exposure_intent` before switching to normal routes, and records `awaiting_acceptance` only after normal TLS probes. An ordinary promotion error invokes `recover_after_exposure`: verify maintenance, stop the five exact successor writer IDs, and compare the private logical baseline. Only an unchanged result can clean the verified successor containers and restore source IDs; changed or unverifiable state resumes and retains the successor. Controlled failure-order tests pass, but the module has no production CLI and does not reconstruct state after a process crash. Real service/TLS and post-write drills remain required.

`ip_forward_transaction.run` now retains a single host lock while staging, preparing, holding source IDs, starting the candidate and promoting ingress. It assigns ordinary pre-exposure recovery to each failing boundary; a partially renamed source is distinguished from a candidate by exact IDs so cleanup cannot delete it. The operation intentionally has no production CLI until power-loss recovery can reconstruct and reconcile those durable phase receipts. Its selected tests verify lock lifetime and failure ownership with controlled services; real exact-image execution remains a separate gate.
Once `candidate_ready` is recorded, the successor is a running writer generation even before public exposure. An ordinary promotion/precondition failure must therefore stop those exact writers and compare the sealed logical baseline before deciding whether the held source can be restored. Changed or unreadable successor state keeps the successor; the transaction wrapper must not replay an already failed recovery automatically.
Crash reconciliation is phased by the first action that can replace source service names. Before `candidate_intent`, an internal locked entry point can validate the sealed six IDs, restart a partly stopped source, restore original ingress and rerun the complete live preflight before recording `source_restored`. From `candidate_intent` onward it must additionally reconcile held names and partially created successors; from `candidate_ready` onward it must stop and fence the running successor. Until those later cases are implemented and exercised against real Docker, the public forward CLI remains closed.
The `candidate_intent` boundary now includes a baseline of the quiesced candidate before any successor service starts. Ordinary partial-start recovery stops identity-validated successor writers and compares that baseline before deleting any successor container or restoring the source. A changed or unverifiable state fails closed; the candidate data remains available for explicit recovery. Power-loss reconciliation must reconstruct this evidence and all held/canonical IDs before applying the same decision.
The internal crash reconciler now reconstructs the `candidate_intent` state under the host lock from the journal, source identity, Caddy digest, source origin ledger and candidate paths. It reuses the same partial-writer fence before exact-profile candidate cleanup and held-source restoration. That boundary alone did not accept `candidate_ready` or later exposure; the next continuation below adds that path, while the production CLI remains gated.
The next internal recovery boundary now reconstructs the sealed successor IDs and post-start baseline for `candidate_ready` through `awaiting_acceptance`, tolerating an interrupted prior writer stop without changing service identity. With its exact successor Caddy still running, it restores maintenance, stops all exact successor writers, compares the baseline and either restores the held source on an unchanged result or retains the successor on a changed/unverified result. The command remains internal until live Docker/TLS interruption drills and a durable active-generation pointer prove subsequent upgrades cannot accidentally select the old source.
The clean-source decision must survive a crash after the first successor container is deleted. Persist a `source_restore_intent` with an unchanged write-fence result before cleanup; the journal disallows jumping directly from a running candidate to `source_restored`. On restart, validate the exact remaining IDs and rerun the candidate baseline comparison before deleting the rest or restoring the held source. Any restarted writer or changed/unreadable data fails closed. This preserves the decision across a partial cleanup without trusting a stale in-memory result.

Use the ordered forward journal itself as the durable current-generation authority for later upgrades. The initial activation still uses its first-cutover ledger; a forward successor is eligible only when its journal says it is serving and its exact six candidate IDs, image, mounts, schema and ingress all match the live host. A stopped/restored/incomplete journal cannot impersonate the active generation. The private first-cutover publication template's image tag remains historical after the first forward step, so later source validation uses the sealed journal plus live image digest instead. Forward identity receipts accept either an initial `candidate-` or prior `forward-candidate-` source directory. This avoids a second mutable pointer whose update could disagree with the phase journal after a crash; real sequential Docker upgrades remain a gate.

The old-schema rollback CLI must preserve the active generation's candidate/backup identity when a post-write rollback is refused. It now carries prior receipt fields across phase events and records `rollback_refused` while leaving the active outcome `awaiting_acceptance` only for the exact `candidate_has_unmerged_writes` result. The real owner publication changed the private baseline; a production invocation refused the old generation, and a fresh current-generation preflight plus browser reload confirmed the existing schema18 publication survived. This does not replace the required forward recovery from that retained state.
