## Design
US1 normalizes UTC values before comparing or emitting acceptance timestamps; results remain honest and stale evidence remains hidden. Broader version-bound checks are tracked separately.
US2 reuses immutable registered artifacts and content policy checks. Introduce a schema version that represents advisory publication without forged verification identities, preserves existing verified release rows and enables strict policy explicitly. Preflight exact content outside the write lock, then repeat owner/head/generation checks inside the transaction. Persist idempotent receipts and audit transitions.
US3 list retained publications newest first with bounded pagination, timestamps, current-live marker and optional check details. Restore creates a new publication event from retained exact content, preserves draft head and uses expected generation to reject races. Historical preview remains owner-authorized unless deliberately published.
Content delivery reuses independent-site binding and host-only console sessions. The owner has no domain and requests IP-only access. Although IP TLS certificates now exist, different ports do not isolate cookies and one port for all projects would share browser storage. A safe IP-only design requires further work; no production activation until its cross-project and console isolation, migration and rollback tests pass. The private COS bucket supplies bytes, not an isolated browser origin.

The first IP-only security increment enforces the configured HTTPS console host on every durable cookie-authenticated API request and the exact console `Origin` on all unsafe methods, including ordinary project/settings routes that previously relied on a valid cookie alone. This closes one cross-port CSRF path; it does not isolate cookie namespace, supply per-project ports or constitute a public ingress design. Keep T012a open until native Web Storage, cookie behavior, direct navigation, control-plane denial and port lifecycle are proven together.

The next versioned migration must reserve stable, never-reused preview/public origins per project. A purpose-separated HMAC proof derived from the active durable session supplies a second console-origin credential without a new secret-bearing table. The API verifies cookie plus proof for reads and writes; existing cookie-only sessions reauthenticate at cutover. Draft preview moves off the console origin, and an owner-initiated isolated browser checks an exact saved revision; generated pages cannot submit their own results. An ingress reconciler renders explicit IP:port TLS listeners from the committed ledger, validates/reloads Caddy and probes the listener before publication becomes live. The database and Caddy cannot share a transaction, so restart reconciliation and rollback are mandatory. The concrete contract and still-open acceptance cases are in ip-only-design.md and T012a2–T012a6; do not activate intermediate code in production.

Schema17 implements the immutable port ledger and transactional, bounded allocator in `backend/app/migrations/project_origins_v17.py` and `backend/app/project_origins.py`. Existing schema16 publication behavior is preserved on schema17, including release history and durable sessions. A protected copy of the earlier production online backup now rehearses schema10→18 with all predecessor backups and core business counts verified; final quiesced-source rehearsal remains open. The standalone public content process resolves an exact IP Host and immutable public port to the current live public binding, then reuses the byte-verified content service; unknown, preview and withdrawn routes deny delivery. Target Caddy reconciliation and external reachability remain open.

The allocator now also provisions all existing projects in one transaction for the protected migration. New projects reserve both ports inside the same SQLAlchemy/SQLite transaction that creates the project when the IP-preview cutover gate is enabled. Capacity failure rolls back the project row. This does not make listeners reachable: the ingress controller and cloud rule must be proven before enabling the gate.

The publication API now has a second, paired IP delivery mode behind `ATOM_IP_PUBLIC_ENABLED`, which requires isolated preview and console proof. It refuses an unallocated project; current public links use its immutable public port; history in this mode requires a fresh owner-issued preview grant rather than returning a reusable private URL. The legacy `/p/{slug}` console route redirects a currently live public release to that port, retaining subpaths and query strings, and returns 404 after withdrawal. In IP preview mode the old console-origin `/preview/` route denies generated HTML. These code paths remain off until the frontend main preview, verifier, external TLS and ingress lifecycle have completed their cutover gates.

Before a **new** IP-mode publication or historical restoration writes its pointer, the repository runs an injected production readiness callback after artifact validation and before its second fenced write. The console callback reads both immutable project ports and probes their service identities with verified TLS and no ambient proxy. A failed listener returns 503 and leaves the previous publication intact. Receipt replays bypass the callback because they do not create a new publication; unpublish remains available during ingress failure. A configured absolute CA file is available for private rehearsal, while production defaults to the system CA trust store. This closes the local publication/listener gate, but a successful on-host probe cannot substitute for independent public-network/browser reachability.

Each isolated service exposes a fixed `/_atom/health` identity endpoint on only its exact assigned HTTPS Host/port, outside generated content paths. `probe_ip_routes` checks trusted TLS, response type, no cookie, and the committed project/purpose from the caller's network location with ambient proxies disabled. Local real TLS tests cover success, mismatched identity and untrusted certificates. This lets the ingress controller distinguish a correctly routed service from a generic HTTP 200. It does not prove external security-group reachability or gate publication on listener readiness; those remain in T012a2/T012a5/T013.

`backend/app/ip_ingress.py` renders deterministic explicit Caddy HTTPS listeners from committed active origin rows. Inputs are a pristine base Caddyfile, canonical IP, validated internal upstreams and configured ACME directory. A retired project is omitted while its port remains reserved. `backend/app/ip_ingress_controller.py` locks the host operation, requires a read-only **directory** bind at `/etc/caddy`, validates with the running Caddy image, atomically replaces the host Caddyfile, reloads, probes every committed route, and restores the previous bytes and reloads on failure. Reconciliation always reloads, even when the desired bytes are unchanged, repairing an interrupted/restarted Caddy process. The current target still binds the individual Caddyfile and must be changed before this controller can apply. The bounded host/container port pool, Tencent Cloud ingress rule and real target apply/restart test remain open.

The owner preview uses its own short-lived, one-use capability and port-specific HttpOnly session, as specified in `contracts/ip-preview.md`. Schema18 and `PreviewAccessRepository` persist purpose-separated token hashes, select only an owned current saved revision or retained publication, consume grants once and recheck the durable source session for access. `materialized_preview` verifies exact private-store bytes and rechecks revocation before serving. The existing content handoff is release-binding scoped and cannot authorize a draft; reusing it as draft authority would create a false release. Under the disabled-by-default IP gate, the workspace now opens its saved revision on the isolated TLS origin, history uses the same one-use action, and the old console preview is denied. Local real Chromium tests cover the workspace popup and underlying preview/public port isolation. The functional-check action now uses the owner-initiated exact-revision verifier route and renders validated attested results; latest results are marked current only when revision, contract, policy and runner match. A pinned local Docker worker and trusted supervisor/attestation path pass selected real Chromium tests. Private verifier API deployment, console click-through, trusted TLS proxy path, external ingress and target cutover remain open under T012a2/T012a3/T012a6.

## COS process boundary
Use cos-python-sdk-v5 through an owned subprocess for each bounded operation. A parent deadline terminates and reaps a stalled SDK worker, including response trickle or retry behavior; SDK socket timeouts alone cannot provide that total lifetime guarantee. The worker receives only storage credentials through stdin, disables diagnostic payloads, refuses overwrite through a signed conditional PUT, and verifies read-after-write bytes. No per-request console/runtime secrets are passed to this process. Local and COS stores implement one snapshot port; migration verifies every old local artifact before authoritative COS reads are enabled.
