# Protected forward recovery after publication writes

Status: read-only current-generation gate implemented; forward transaction **not implemented or production-accepted**.

## Trigger and source of truth

When the old-schema rollback fence reports `candidate_has_unmerged_writes`, the active schema18 candidate is the only authoritative application and broker state. The preserved schema10 pair is an audit/recovery artifact, never a source for the next deployment. A new operation must identify the active candidate by exact container IDs, image digest, database schema, data and broker bind paths, origin ledger and current release generation before stopping a writer.

`deploy/ip_forward_preflight.py` is the implemented read-only gate. It checks the active phase/identity receipts, six live service identities, image labels, binds, schema/idle-writer state, complete project-origin allocations, generated Caddy bytes and all published port binds under the host lock. Its optional successor inputs require a clean exact Git revision and matching image label. The old private publication template still names the schema10 bind paths; the gate uses live Docker mounts and the current-generation receipt for data authority. A passing result does not exclude a writer after the lock is released. The future transaction must repeat the gate and quiesce writers before capturing a backup. The historical cutover Caddy digest is not the current digest after new project origins are assigned.
The gate's `_inspect_locked` operation is now separated from the public `inspect_current` command, which acquires the host lock around it. The forward transaction must call `_inspect_locked` while holding that same lock through maintenance and writer quiescence; releasing and reacquiring between those steps would reopen the checked-to-stopped race. The standalone command remains read-only and cannot itself exclude later writes.
`app.artifact_transfer.verify_registered_remote` is the separate read-only COS inventory primitive. It reads and validates every registered snapshot, detects ledger changes across the scan, and never invokes `put`. The future transaction must bind its receipt to the quiesced source inventory; running this on a live ledger is only a preparatory check.

## Transaction

1. Under the same host-exclusive deployment lock, validate a clean exact Git revision, exact image and SHA-locked runtime, current service identity/health, schema compatibility, retained data paths, COS inventory and the full committed origin set. Reject if any pointer or source changed.
   Before changing ingress, atomically persist a root-private `ip_forward_identity` receipt for the six exact source Docker IDs, their reserved forward-held names, source/successor revision and image, expected backup/candidate paths and original console/Caddyfile bytes with hashes. Recovery must validate this receipt before renaming or restarting an older generation. The receipt alone does not authorize data rollback after exposure.
2. Put console and every allocated project HTTPS origin in a write-blocked maintenance state with verified TLS and 503/no-store. Quiesce API, broker, preview, public and verifier writers, including in-flight operations and leases. Do not capture a source state while any writer can still commit.
3. Capture and independently verify a fresh root-private paired application/broker/Caddy backup. Restore only that captured **current candidate** state to a separate generation. Preserve source and backup byte-for-byte. Run only an explicit migration from its actual schema when the new image requires one; for a schema-preserving image change, assert schema/foreign keys and immutable artifact/COS and origin-ledger equivalence.
4. Start the new private verifier and content services and the new API/broker pair against the separate generation. Retain the previous compatible schema18 containers stopped by exact ID. Reconcile all committed HTTPS origins, verify their project/role identities and existing public bytes, then seal a new pre-console baseline. Promote the normal console only after strict-TLS readiness.
5. Record each phase, exact image/data IDs, backup manifest and terminal outcome. On failure before exposure, restore the previous compatible generation and HTTPS routes by exact ID. After exposure, use a fresh write fence: if the new generation has owner writes, retain it and refuse an older data generation. Recovery never automatically copies SQL rows between schemas or manufactures publication receipts.

`app.ip_ingress.render_ip_maintenance_routes` and `probe_ip_maintenance_routes` now provide the project-origin configuration and write-denial check for step 2. They have not been connected to a host transaction or applied to production. The render preserves exact allocated TLS authorities and ACME settings while replacing upstream proxying with 503/no-store; the probe requires each HTTPS origin to reject POST with 503/no-store and no cookie.
`IpIngressController.maintain()` now applies that rendered configuration through the existing file lock, Caddy validation, atomic replace, reload, per-origin probe and restoration-on-failure path. The CLI exposes this as `--maintenance` with a caller-supplied write-blocked console base. The forward host transaction must create and validate that console base and must still independently probe console GET/POST before stopping writers.
`IpIngressController.transition_base()` now switches a supplied console base and project-origin policy under the same ingress lock and one reload. It installs denying active routes before persisting the maintenance base, and persists the normal base before exposing normal active routes. A failed write/reload/probe restores both prior files. This is in-process exception recovery; the host transaction still needs a durable maintenance-intent/phase receipt and crash recovery before it can claim power-loss-safe writer exclusion. It must independently probe console GET/POST before stopping writers.
`deploy/ip_forward_writers.py` now provides the exact-ID stop/resume primitive for the five writer services. Its caller must retain the host lock and verified maintenance ingress. It stops verifier, preview, public, broker and API in that order, confirms each exact container ID is stopped, then rechecks schema18/schema3 and idle attempts. If a stop command fails after the daemon has already stopped a container, the attempted ID is still included in recovery; restart runs in reverse dependency order and is idempotent. It leaves Caddy serving TLS maintenance. Selected local fake-Docker fault tests and one isolated real-Docker five-container stop/resume drill passed; the host transaction must still record its exact IDs and prove actual production writer exclusion before relying on it.
`deploy/ip_forward_capture.py` is the next internal phase. Immediately before copying, it re-inspects the five stopped exact IDs, compares the complete origin-port tuple against the stopped schema18 database, checks the running Caddy ID and read-only directory bind, compares both maintenance Caddyfiles to deterministic rendering, and probes strict-TLS 503 on console and every committed origin. It then captures, independently verifies and restores a fresh schema18/schema3 application/broker/Caddy pair into a separate successor directory. The restored ledger is checked against private COS by the exact successor image in a read-only, networked container, with object count and inventory digest returned in the capture receipt; this code path has selected local command/receipt tests, not a quiesced target run. The caller must keep the host lock, persist the receipt, and continue to promotion or recovery; the module has no standalone production command.

## Verification boundary

`deploy/ip_forward_journal.py` now defines the root-private durable phase record. It binds the exact six-ID/Caddy identity receipt digest, appends only ordered phases and fsyncs each replacement and parent directory. Intent phases precede maintenance, writer stop, candidate handoff and exposure; capture records exact backup/candidate paths and backup/Caddy/COS digests and counts. Source restore after exposure intent requires an unchanged-write-fence receipt. The journal does not inspect Docker or implement recovery; the host-locked caller must reconcile live state and prove the write-fence claim. It has not been used in a production transaction.
`candidate_ready` additionally requires a separately validated successor image/directory, six **new** exact container IDs disjoint from the source, a sealed logical-state baseline digest and a Caddy digest. Only the future handoff code may supply this receipt after health and strict-TLS maintenance probes; merely writing the record cannot prove those live checks.

`deploy/ip_forward_stage.py` wires the first transaction phase under a caller-held host lock: current/successor recheck, exact identity and phase receipt, combined console/origin maintenance, independent console denial probe, five-writer exclusion, quiesced backup/restore and COS receipt. On an ordinary pre-exposure failure it restarts the exact source IDs while maintenance remains active, restores the original base/routes, rechecks the complete current generation and then records `source_restored`. A crash leaves the journal intent for explicit recovery; candidate handoff, post-exposure write fencing and a public transaction command are still absent. Its selected fake-service tests cover ordering and capture-failure recovery; they do not prove actual production exclusion.

`deploy/ip_forward_candidate.py` prepares the separately restored schema18/schema3 pair without touching containers. It re-verifies backup and candidate manifests, matches the journal's captured paths/digests, checks unchanged release/origin ledger shape and creates root-private maintenance Caddy and service environments. The first-cutover private template still contains an inactive Caddy IP and cannot be treated as live authority. `ip_forward_identity.capture` therefore records the four pinned API/preview/public/Caddy bridge addresses with their exact IDs **before** stopping any writer. Preparation rechecks the five stopped writer IDs and running Caddy ID/address, then uses the sealed addresses to replace stale Compose inputs. A Docker stopped container may lose its visible `IPAddress`, so reading service addresses after quiescence would be incorrect. The candidate is still unexposed. Candidate service handoff, sealed baseline and write-aware recovery remain future transaction phases.

`deploy/ip_forward_hold.py` adds the next internal boundary. After recording `candidate_intent`, it stops the exact Caddy ID, verifies it stopped, then renames all six stopped source IDs to the identity receipt's reserved held names. On an ordinary stop/rename failure, including timeout after effect, it inspects each exact ID, restores canonical names, restarts the source Caddy and writers, restores normal ingress, re-inspects the whole source generation and only then records `source_restored`. A crash remains journal-guided recovery work; the module does not create successor services or expose a partial CLI.

`deploy/ip_forward_start.py` now starts the six successor roles under a revision-specific Compose project so held source project labels cannot be mistaken for the new project. It uses the sealed bridge IPs, private environment files and a separate restored schema18 pair. Before recording `candidate_ready`, it verifies six new IDs, exact image/data binds, private/public network profiles, five health statuses, complete TLS maintenance on console and committed origins, unchanged origin ledger, and a sealed application-plus-broker logical baseline. An ordinary pre-exposure startup failure removes only containers with verified successor image, bind and Compose ownership before invoking exact source restoration. Crash recovery and any post-exposure decision remain open; the module has no standalone deploy CLI.

`candidate_write_fence.read_baseline` now refuses an untrusted file mode, non-root owner, mismatched revision/image/directory, or a digest that differs from the journal candidate receipt. `compare_baseline` re-fingerprints the candidate only after that identity check. The caller must keep the candidate writers excluded for the whole comparison and must independently verify the live six-ID generation before choosing source restore. The helper itself does not perform writer exclusion or a deployment decision.

An isolated drill must create a real Atom release/history write, observe old-schema rollback refusal, then run the new forward transaction from the retained state. It must prove the release and draft survive, another owner operation succeeds, the public page serves the selected immutable bytes, project origin assignments are unchanged, and a fault at each ingress/writer phase leaves a usable generation. Production acceptance additionally requires authenticated owner/browser and certificate-renewal evidence. Until those pass, T013f and T014 remain open.
