# Data Model
- Existing acceptance_runs timestamps represent UTC even when SQLite returns naive datetime objects; normalize at read/comparison, preserve stored values.
- Immutable saved revision and artifact remain the content authority.
- Publication snapshot references a retained revision, creator, timestamp, previous publication and an explicit check policy/state; absence of functional evidence must not be encoded as passing evidence.
- Live publication has monotonic generation, live flag, stable sharing address and selected snapshot.
- Each snapshot retains its committed publication generation, unique per project; history uses that number for order and pagination even when wall-clock timestamps tie or move backward. Migration derives existing values from durable command receipts, never random-ID ordering.
- Restore is a new durable event selecting historical content, not mutation of history or editing draft.
- Precise policy/schema migration is reviewed under T004 before publication implementation.

## Schema16 policy fields
release_records.verification_mode is advisory|required, defaults to required for existing rows. Verification identity and two verifier digests are nullable together; advisory stores NULL, required stores exact existing evidence. Direct revision/project/workspace relationship remains enforced independently of evidence. Rollback provenance preserves source/displaced/new IDs and monotonic generation, using NULL-safe comparisons. Existing immutable artifacts and bindings are retained; no separate ordinary-publication table or mutable-files bypass.

## IP-only origin ledger (schema/repository implemented; serving pending)
The additive schema17 introduces one immutable reservation row per `(project_id, purpose)` where purpose is `preview` or `public`. A single global `UNIQUE(port)` constraint spans both purposes and every project; `PRIMARY KEY(project_id,purpose)` prevents reassignment of a project's role. A reservation is never deleted or updated, including after project deletion. Inserts require a real project at the time of reservation but cannot use a cascading foreign key because the port must remain unavailable forever even if the project is removed. A separate trigger denies later reuse of a retired project ID. The repository reserves both roles in one writer transaction, with a bounded configured pool and deterministic exhaustion error. The serving layer must never infer ownership from a port alone: it must resolve the immutable reservation, then check project existence, requested role, owner capability for preview, and current public release for public content. Old per-release binding IDs remain evidence for legacy link continuity, not the stable browser origin. Ingress must render listeners only for extant eligible projects while keeping retired ports reserved in the ledger.

No fixed port numbers or pool size belong in the schema; deployment configuration and Tencent Cloud ingress/firewall must agree on the capacity. A failed Caddy reload or TLS probe must not advance the public release pointer. Restart reconciliation computes desired listeners from the authoritative ledger and records failure without reassigning a port. A pure renderer now creates explicit HTTPS port listeners from active rows, rejecting malformed addresses/upstreams and duplicate ports. Migration, reservation, standalone public-read routing and rendering tests are passing; atomic ingress apply, owner preview routing, browser and production tests remain open under T012a5.

## Owner preview capability (schema/repository implemented; serving pending)
Additive schema18 stores one-use preview handoffs and short-lived sessions as hashes of independent random secrets, plus append-only content-free success audit events. Each grant/session row pins a project, saved revision and source console session; it contains no generated HTML, raw tokens or COS credentials. The repository issues only for a current saved workspace revision or retained publication revision and requires an existing preview-port reservation. Exchange consumes exactly one handoff and creates a session in one writer transaction. Both transitions write audit events atomically. Authorization rechecks the source session, project owner and exact registered artifact descriptor. `materialized_preview` reads exact private-store bytes, verifies archive size/revision/content policy and rechecks authorization around extraction. Its future per-project preview-port cookie must be HttpOnly, Secure and validated against the immutable origin ledger on every read. The draft head may advance without changing an already issued preview; a new owner action issues a fresh capability for a newer revision. See `contracts/ip-preview.md`. The HTTP exchange, content server and browser behavior are not implemented or accepted yet.
