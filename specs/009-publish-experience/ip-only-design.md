# IP-only publication design candidate

**Status:** architecture under review; no production activation or acceptance claim. The owner chose the server IP and has no domain. The design must preserve native `localStorage` for generated applications, including after a release is restored.

## Existing boundary that must change

The current `/preview/{project_id}` response and workspace iframe are both on the console origin, and the iframe has `allow-scripts allow-same-origin`. The console reads `contentDocument` to run the UI's functional checks. Thus isolating only the future public URL would leave generated preview code on the privileged console origin. Moving preview and checks is mandatory. The existing content service uses a distinct DNS host per **release**; on an IP address, a stable **project** origin is needed so publication updates and restores preserve browser storage.

## Candidate topology

- Console stays at `https://159.75.231.98/atom/` on port 443.
- Each project reserves two immutable HTTPS ports: one for its owner-only draft/historical preview, one for its public live page. A project's ports never change across releases and are never assigned to another project, even after unpublish or deletion; browsers can retain storage indefinitely. A bounded pool and an honest capacity error are required. No project shares an origin with another project or the console.
- The trusted content process serves exact registered snapshot bytes from private COS. It selects the project from a durable port-to-project ledger, then selects the live release or one authorized preview release. The public endpoint returns only public live bytes. The preview endpoint uses a binding-scoped, HttpOnly capability and never treats a release ID as authorization.
- Caddy gets explicit HTTPS IP listeners for committed project ports and passes an unmodified, validated Host. Unknown ports fail closed. The console listener does not proxy generated paths. A controller renders complete configuration from the ledger, validates it with `caddy adapt`, reloads atomically, probes each new listener, and reconciles after restart. Publication cannot become live until its listener is serving the intended project. Rollback pairs database state with the prior ingress configuration. [Docker Compose's short port-range syntax](https://docs.docker.com/reference/compose-file/services/#short-syntax-3) can map an equal bounded host/container range; the long `published` range allocates a single available port and is unsuitable for stable per-project origins. This target is a Tencent Cloud Lighthouse instance, whose [instance firewall](https://cloud.tencent.com/document/product/1207/44577) controls inbound public traffic. Its IPv4 TCP 20000–20127 allow rule was added and both boundary ports passed external HTTP reachability probes; project HTTPS and production Caddy routing still require separate verification.
- The two internal content processes accept `X-Forwarded-Proto` only from Caddy's pinned bridge IP. Their inherited API healthcheck is replaced with a port-8000 process check; the controller's exact HTTPS identity probe verifies routing separately. The target's port-80 nginx proxy already relays ACME HTTP challenges to `atom-tls:80`, so the Caddy replacement must preserve its network identity, certificate volumes and that relay. A separate migration-copy rehearsal proved trusted Caddy scope, denial from another bridge peer, process restart and one real COS read; public TLS and cloud ingress are still outstanding.
- The console session remains HttpOnly, but a separate console-origin proof is required on **every** authenticated API request. The server derives a purpose-separated HMAC proof from the persisted session identity and its private signing key; login returns the proof to trusted console JavaScript only after the proof requirement is enabled. JavaScript keeps it in console-origin storage and sends it as a custom header. Cookie-only sessions from before cutover must reauthenticate; no endpoint discloses their proof. The proof prevents a cross-port script from using or fixing a shared-host cookie alone, including browsers without `__Host-Http-` enforcement. All unsafe authenticated requests also require the exact console Host and Origin. No credentialed cross-origin CORS allowance is issued.
- Legacy published `/p/{slug}` URLs remain reachable, but must redirect to the matching isolated project origin after exact old bytes and link continuity are verified; they must not execute generated HTML on the console origin. The current same-origin draft preview is removed only after the isolated owner preview and functional checks have browser-tested replacements. No `allow-same-origin` sandbox on a console-origin generated document is accepted as an isolation boundary.

## Atomicity and isolation tests before adoption

1. Browser matrix: Chrome, Firefox and WebKit direct navigation, native `localStorage` persistence across public publish/update/restore, project A/B separation, preview/public separation, same-IP cookies across ports, and old/new sessions. Test desktop and mobile.
2. Hostile generated page: attempt to read parent DOM, console storage/API responses, another project's storage, private historical HTML, content-session cookies and COS credentials; attempt cookie planting, credentialed simple POST/form/GET, preflighted custom-header requests, popup/opener navigation and service worker registration. Console writes must reject foreign Origin/proof before mutation.
3. Release lifecycle: concurrent port reservations, pool exhaustion, listener reload failure, TLS renewal, port conflict, process crash between listener and database commits, unpublish, re-publish, restore and rollback. No failed stage may expose a different project or change the prior live release.
4. Production ingress: certificate-verified IP HTTPS on all chosen ports, Tencent Cloud firewall reachability, no console Cookie forwarded to content logs, exact Caddy config digest and restart reconciliation. Private COS remains inaccessible directly to anonymous users.

This is a candidate because Caddy syntax, local browser storage behavior and console-origin CSRF can be addressed in parts; the complete browser, credential and deployment gates are still open. Do not mark T012a2/T013/T014 complete based on this document.

## Implementation contract for the next migration

The database, ingress and browser must agree on **one stable project identity**. Reserve preview and public ports in the same transaction that creates an immutable project-origin row; never derive ports from release IDs or the current count of projects. The row is append-only, including after project deletion. Unique constraints cover both ports across all rows. Exhaustion returns a documented capacity error before creating a publication. The reservation must survive restore, unpublish and process restart. Ingress configuration is rendered from committed rows, validated and reloaded before a publication is exposed; an unsuccessful probe leaves the old live pointer untouched. Reconciliation on restart is required because a database commit and a Caddy reload cannot share one transaction.

Do not reuse the existing per-release content binding as the browser origin. A stable project origin must resolve the *current* live release at request time, then perform the existing exact-artifact and audience checks. Owner preview uses a second project origin and a short-lived, HttpOnly, binding-scoped capability; its release selector remains owner-authorized. Content responses must not set or forward the console session cookie, and content requests must not enter console authentication middleware. A route that receives an unexpected Host, port or forwarded-host value fails closed.

The console needs a second, independent credential because cookies on the same IP are shared across ports. Derive a purpose-separated HMAC proof from the active persisted session ID and a private server key; return it only on login/register through the console API when the new mode is enabled. Store it in console-origin storage and send it in a custom header on **every** authenticated console request, including reads and logout. Verify it in constant time after validating the signed HttpOnly cookie and active session, alongside the exact Host and unsafe-method Origin checks. Sessions issued before activation have no client-visible proof and must sign in again; there must be no compatibility path that accepts cookie-only sessions after activation. Key rotation invalidates both cookie and proof. The API must never grant credentialed cross-origin CORS to generated content. This does not substitute for removing the existing same-origin `/preview/` execution route: generated scripts must move to the preview port in the same cutover.

The present functional checker reads `iframe.contentDocument`, which will be unavailable across the required origin boundary. Replace this with an owner-initiated server check run in an isolated browser/verifier process. The runner opens the preview origin using a narrowly scoped capability, executes the real DOM interactions against the exact saved revision, and persists observations through a version-bound server API; the console polls the run by its authenticated owner identity. A generated page must not be able to submit or forge its own result via `postMessage` or receive a console API token. Resource limits, timeouts and terminal failures follow the existing verifier boundary. Ensure the owner preview itself can run native browser storage and scripts, including on reload. A failed or timed-out check remains an optional check failure, never a hidden publication prerequisite under the advisory policy.

The rollout order is schema and proof support, authenticated isolated preview/checks, stable public project origins with legacy `/p/` redirects, Caddy/TLS/firewall reconciliation, then COS authoritative reads and publication. The final cutover is a protected maintenance operation; independently shipping any intermediate state that serves generated scripts on the console origin or authorizes cookie-only console requests is disallowed. Browser and rollback evidence is required before the task can be marked complete.
