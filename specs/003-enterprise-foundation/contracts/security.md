# Security contract — design revision 1

Status: proposed and unimplemented. Covers FR-001/002/003/007/010/012 and US1. Review against threat tests before declaring accepted. These rules do not authorize third-party account changes.

## Trust boundaries

| Zone | Allowed authority | Explicitly excluded |
|---|---|---|
| Control plane | Authenticated organization/project actions; policy decisions; command registration | Executing generated code; serving generated HTML on console origin |
| Model gateway | Fetch one approved credential version for one approved endpoint and run | Accepting arbitrary endpoint plus fallback platform credential |
| Runtime adapter | Own runtime/Pi with task-scoped tools, bounded execution and event emission | Control-plane DB/session/encryption keys; host Docker socket |
| Workspace worker | One attempt workspace, pinned image, resource limits and approved network destinations | Other workspaces, platform data volumes, metadata endpoint, arbitrary host mounts |
| Preview/application hosting | Serve immutable project artifacts under separate untrusted site | Console cookie scope, console origin, deployment signing identity |
| Evidence runner | Read an immutable artifact and execute fixed verification plan | Agent control over test results, control DB write credentials, arbitrary unsigned test callbacks |
| Deployment worker | Promote a previously authorized exact digest to one environment | Building a different artifact after approval, rewriting acceptance evidence |

A generated app and its dependencies are hostile inputs even when generated by our agent. Prompts and tool descriptions are not enforcement. Runtime changes remain outside locked `runtime/pi`.

## Provider connection contract

A connection is the indivisible tuple `{connection_id, organization_id, endpoint, credential_ref, credential_version, network_policy_id, model_policy_version}`. Resolve it once through a shared service for model listing, planning, building and races. APIs never independently merge endpoint and key defaults.

1. Organization-managed connection references an administrator-approved endpoint and secret. A member selects its ID; cannot alter its endpoint. Platform secret is never returned to the browser.
2. User-owned connection references that user's organization-scoped encrypted secret and an approved custom endpoint. Missing/revoked secret returns `provider_credentials_required`; no fallback to managed credentials. Credential-less internal services require an explicit administrator-created connection type, not an empty-string fallback.
3. Editing an endpoint creates a new connection revision. The old authorization does not silently apply. Running requests keep a non-secret configuration snapshot; secret revocation is checked before the next call.
4. Normalize scheme/host/port/base path with a URL parser. Reject userinfo, query, fragment, control characters, ambiguous encoding and non-HTTPS production endpoints. Base paths are part of credential binding, not just hostname. Internal HTTP endpoints require explicit administrator network policy and isolated private transport; cannot be enabled by a project member.
5. Disable HTTP redirects for credentialed model calls. Validate all resolved addresses, and enforce the approved destination on the actual network connection, not only an earlier DNS lookup. Block private, loopback, link-local, multicast, unspecified and metadata destinations for public-provider policies; an internal policy grants only named service destinations, not an entire private range by default.
6. Apply the same egress boundary to model discovery and generation, including runtime-side calls. DNS re-resolution cannot bypass policy. A separate egress gateway with authenticated service identity is the preferred enterprise boundary; URL validation alone is insufficient.
7. Failed discovery returns an explicit unavailable state and, optionally, a timestamped last successful real catalog. Never invent model IDs or label unverified models available. Credential-specific cache scope includes connection version and authorized principal, never a secret suffix.
8. Logs contain connection ID, sanitized host, model, request correlation, duration and error category. No headers, secret values, full prompts or URL credentials in default telemetry.

## Authorization matrix

Organization role and project grant are both required; organization membership alone does not expose every project. A role is a set of capabilities evaluated server-side. Roles below are initial presets, not hard-coded conditionals spread across endpoints.

| Operation | Viewer | Developer | Reviewer | Release manager | Organization owner |
|---|---|---|---|---|---|
| Read granted project and redacted evidence | Yes | Yes | Yes | Yes | By explicit project access |
| Propose requirements, edit workspace, launch bounded run | No | Yes | No | No | Requires developer grant |
| Approve exact revision acceptance | No | No | Yes | No | Requires reviewer grant |
| Promote approved release to allowed environment | No | No | No | Yes | Requires release grant |
| Manage members, policy and connections | No | No | No | No | Yes |
| Read secret plaintext via product API | No | No | No | No | No |

Users may hold multiple grants. Production can require distinct author/reviewer identities; violation is a policy failure, not a hidden UI rule. An organization owner can administer grants, with an immutable audit event; this does not silently authorize production execution. Never allow revocation of the final active owner without a valid ownership transfer. Membership revocation invalidates sessions/grants and is checked on each sensitive operation. Cross-scope IDs return 404; known in-scope forbidden actions return 403. Expired authentication returns 401. Refused operations produce no side effects.

## Preview, cookies and CSRF

- Console and generated applications must use distinct configured sites. Prefer separate registrable domains; sibling subdomains are same-site and are not sufficient CSRF defense.
- Console session cookie is Secure, HttpOnly, host-only with `__Host-` prefix and Path=/ in production. No Domain attribute. Server verifies Origin against exact configured console origins for state-changing browser operations and requires a session-bound CSRF token. No state changes via GET.
- Preview access exchanges an authorized, one-use short-lived capability for a preview-only session; scope is organization/project/revision/audience. Do not place reusable console credentials in query strings. Limit referrer information and never log capability values.
- Public published apps never receive control-plane sessions. Direct top-level app visits must be isolated too; iframe flags alone do not protect them.
- CORS grants no arbitrary credentialed access. Preview responses cannot grant parent DOM access. Evidence runner communicates using authenticated run IDs and artifact digests, not parent-window DOM reads or unauthenticated postMessage results.
- Deletion or unpublish does not make draft files public. Public access is determined by live release audience, not by the historical presence of a project slug.

## Worker and service identity

The broker accepts immutable image IDs, server-resolved workspace IDs, a fixed mount schema and policy IDs. It must not accept arbitrary Docker arguments, host paths, network modes or capabilities from users/agents. Broker and runtime require non-empty authenticated service credentials, rotation and bounded request lifetimes. Bind worker callbacks to attempt ID plus fencing token.

Run containers as non-root with dropped capabilities, no privilege escalation, restricted syscalls, read-only image, bounded writable workspace/tmp, PID/CPU/RAM/storage limits and bounded outbound access. No host socket or platform secrets. Validate the runtime environment has the required isolation; fail closed if unavailable. Rootless containers reduce privilege but do not by themselves prove tenant isolation; hostile multi-tenant execution requires a stronger boundary evaluation (dedicated worker VMs or sandboxed kernel) and real escape/egress tests before shared public SaaS acceptance.

Secret material is injected only into its required trusted component and kept out of generated workspaces. Encrypt BYOK at rest with authenticated encryption and key versioning; wrapping keys live outside application DB/backups. Rotation migrates ciphertext under a controlled process, records versions and tests old-key retirement. Worker cancellation revokes ephemeral capabilities and terminates child processes; it does not falsely claim to retract already sent external requests.

## Required negative evidence

SEC-01: controlled local capture proves changing user endpoint cannot receive a synthetic platform key, for discovery/planning/build/race.
SEC-02: malformed URLs, redirects, IPv4/IPv6 and DNS changes cannot reach forbidden controlled targets; approved internal service still works with its own policy.
SEC-03: generated page cannot read console DOM/cookies, invoke state changes or access another project, in iframe and top-level navigation.
SEC-04: tenant/role matrix covers read/write/stream/file/export/retry/publish/connector/evidence endpoints, including revocation during execution.
SEC-05: worker cannot read host canary, other tenant canary, broker socket or runtime secret; process and network/resource limits actually enforced.
SEC-06: missing production keys, insecure cookie/origin configuration and unauthenticated runtime requests fail closed; no silent development fallback.
SEC-07: scanner over DB dump/log/export finds no synthetic plaintext secret, while encrypted credentials remain usable and rotatable.

## Primary guidance, consulted 2026-09-30

[OWASP SSRF](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html) supports redirect control and domain/address validation; the actual-connect enforcement above is a design requirement to close validation/use races.
[OWASP CSRF](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html) explains why cookie attributes alone and sibling-domain assumptions are inadequate.
[Docker security](https://docs.docker.com/engine/security/) and [rootless mode](https://docs.docker.com/engine/security/rootless/) motivate restricted broker inputs and non-root execution; they do not certify this proposed deployment.
