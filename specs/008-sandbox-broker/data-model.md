# Entities and states
Execution reservation uses existing revision_attempts fields: broker_attempt_id is null until bind, while grant_id, generation, base, deadline and issued_at (created_at) are already durable. Attempt views add project_id and the immutable base artifact/revision from revision_records. An unbound reservation owns its workspace slot and cannot register output. Dispatch reload/binding require current owner/run/head/generation and unexpired active state; exact retries preserve original issued_at. Schema v1 is unchanged, and no signed token is stored.

Control-plane transport results are Provisioned (broker ID, state, deadline) and CheckpointAcknowledgement (broker ID, version, semantic revision). Neither is an API revision or independent acceptance. The client requires a matching API Receipt for confirmation and retains administrative/signing authority only in the trusted process; runtime leases must never contain this client or its credentials.

Broker checkpoint acknowledgement uses the existing checkpoint_revision and version fields. First explicit confirmation advances quiescing→checkpointed once; exact repeat with the original export version/digest returns the same state. Expired/revoked/stale confirmation is denied even on replay. A durable API receipt can therefore coexist with unconfirmed broker bookkeeping after cancellation; cleanup and API execution outcome must be reconciled separately. No new schema is required.

Artifact storage metadata is key (exact archive SHA-256), revision (canonical manifest SHA-256) and byte size. The store acknowledges only verified immutable archive bytes after file/directory synchronization. Reserved staging names are recoverable under exclusive lock; completed objects have no deletion API. Artifact existence is not a Revision record or workspace head. Offline API migration v1 and the trusted revision repository now implement separate workspace/attempt/revision/receipt/outbox authority (contracts/revision-registration.md). Application startup and production orchestration remain unintegrated.

API revision attempts bind current owner/project/workspace/run, generation, base, broker attempt/grant and deadline. Active → cancel_requested → closed is independent of pending/unknown/confirmed termination. Unknown termination retains the active slot. Registration atomically records a child revision, exact-request receipt and undelivered outbox row and advances only its workspace head. It leaves the attempt active until trusted termination evidence closes it. A failed/cancelled run may retain its committed revision; this does not imply independent acceptance. Exact receipt lookup/replay survives closure and newer generations without modifying their head.

CheckpointExport is an in-memory verified result (attempt ID/version, canonical revision, bounded payload excluded from repr), not a persisted project revision. Ready transitions to quiescing before helper execution; successful export remains quiescing with checkpoint_revision unset. New file operations are denied. Re-export rechecks current authority/version; process loss retires the worker without implying storage or registration success. No registry schema change is required for this export stage.

Runtime BrokerLease is transient trusted metadata (run/workspace IDs, internal attempt ID, signed token, deadline), never persisted by the adapter. Adapter states new/active/uncertain/closing/closed govern local dispatch only. Durable authority stays in the broker registry. Scoped release validates the exact stored claim fingerprint and attempt ID, atomically inserts revocation and termination intent even for repeat cleanup; it cannot authorize mutation or affect a higher-fence successor. No registry migration is required.

Grant v1: jti, organization/project/run/attempt IDs, positive fencing integer, base_revision SHA-256, profile files-v1, issued-at/not-before/expires integer timestamps, fixed issuer/audience/subject/type. Validity requires issued-at ≤ now < expiry, nbf=iat, bounded original lifetime. Immutable claims; no host path, secret, image, resource flag or arbitrary capabilities.

Registry (planned): versioned schema; grant ID unique; canonical claim digest; organization/project/run/attempt/fence; base revision; deadline; owned container name; state; latest checkpoint; termination outcome; revoked flag; operation receipt IDs. Token/key material never persisted.
Registry v3 implements broker_meta, attempts, heads, revocations, orphans and operations per contracts/registry.md and contracts/operation-receipts.md. Exact v1/v2 upgrades atomically preserve existing history and add missing tables. Revocation is a durable tombstone table, not a boolean column; confirmed/unknown termination is explicit state. Orphan observations have immutable container ID, claimed attempt ID, observed/termination_unknown/terminated state, version and timestamps; they never manufacture a grant, normal attempt or accepted revision. Operations retain request hashes, admission version, bounded response reservations, completed results and running/completed/unknown state. Read results contain workspace data and require private storage; this is not an encrypted retention system. A checkpoint digest in the registry does not itself register an accepted control-plane revision.
States: intent→provisioning→ready→quiescing→checkpointed; administrative termination interrupts nonterminal states through terminating→terminated/termination_unknown. There is no registry failed state. Unknown outcomes require reconciliation before renewed dispatch. Cancel/revoke forbids new operations immediately. Registry receipt is not control-plane authority; registration must use current execution fence.

Seed lifecycle uses the existing provisioning intent and immutable base_revision; no schema migration is needed. A fixed helper validates and promotes the archive before the current-version ready transition. A crash leaves either provisioning (retire on recovery) or durable ready (also retired on process restart under current recovery policy). No snapshot revision is registered by seed. Repeated seed against ready is rejected without effects; trusted provision/status resolution can observe ready for the same immutable grant.

HTTP authority does not add persisted entities: administrative seed uses a read-only provisioning authorization check, and scoped file requests reuse the existing receipt identity and current ready attempt. Transport admission is process-local and bounded to one active transfer; it does not replace durable lifecycle state or support multi-process ownership.

Recovery is a transient cleanup observation containing attempt/workspace/grant/broker IDs, deadline, state, termination state, outcome and optional immutable Receipt. It omits issuance/base/fence inputs and is not execution authority. Query and cancel result use a single SQLite snapshot and recheck current project owner even for closed attempts. No schema migration or signed-token persistence.

Cancellation coordinator adds no schema: cancel_requested/pending records pre-network intent; broker uncertainty records cancel_requested/unknown; verified revoke permits closed/confirmed/cancelled. An already closed observation is preserved, including a different concurrent outcome and its receipt. API cancellation and broker revocation are separate commits; process loss between them retains the active slot for reconciliation.

ExecutionLease is transient run/workspace/broker-attempt/deadline plus scoped signed grant, with grant excluded from repr. It is returned only after ready observation and fresh API execution check; runtime must still check live broker status. It contains no admin credential or signing key. Preparing uses existing reserved/bound attempt states, with no additional schema. Failure closes failed only after actual cleanup; unknown outcomes retain the slot.

Completion authority returns the persisted Attempt only while current run/generation/deadline/active state hold; its expected head can be that same attempt's receipt revision. It does not restore file dispatch. CheckpointState is a transient admin observation of broker ID/state/version/digest; the coordinator requires a matching API Receipt and verified artifact bytes to recover acknowledgement. No schema change. Successful closure now requires both receipt and active (not cancel_requested) state.

Outcome semantics are now explicitly state-dependent: nonclosed outcome is a durable terminal decision, never a completed result. Only state=closed AND termination_state=confirmed establishes completion. A decision retains the active slot and blocks dispatch/completion authority. Unknown termination preserves it. First non-cancellation decision wins; cancellation overrides a nonclosed decision and must remain the final outcome once confirmed. Existing v1 outcome constraint already permits nonclosed values; schema and historical migration hashes are unchanged.

ExecutionLease now carries completion_grant in addition to sandbox grant; both exclude token bytes from repr. The completion JWT binds the same jti/org/project/run/API-attempt/fence/base/iat/deadline, but fixed audience atom-execution and type atom-execution+jwt distinguish its purpose. The broker token remains atom-sandbox/atom-sandbox+jwt, and the sandbox Grant fingerprint remains unchanged. This is transient authority, not an additional database entity or completion receipt.

Execution HTTP adds no persisted entity: verified completion claims must match durable grant/project/run/API-attempt/generation/base/issued-at/deadline and current project owner, with non-null broker binding. Responses serialize confirmed Recovery (including optional Receipt); nonclosed intended outcomes are never returned as successful HTTP results. Token expiry remains enforced even for closed result replay; trusted background cleanup uses repository identity independently.

ExecutionLease now explicitly includes execution_id (API attempt identity) and grant_id alongside broker attempt_id. Node ExecutionBinding uses these to validate the full response without treating decoded JWT payloads as trusted metadata. ExecutionReceipt contains exact attempt/workspace, revision ID, raw artifact SHA-256 and semantic snapshot SHA-256. A complete response must be succeeded with a non-null matching receipt; cancellation results retain their actual outcome and optional receipt.

withExecution returns the operation value plus the verified completion receipt only after release. Its transient failures preserve operation, cancellation and release causes in order; it introduces no persisted authority or invented resource identity. One outer scope must cover all model recovery calls.

ExternalSandboxScope is trusted transient run/workspace/sandbox identity, constructor-supplied and immutable inside ProductAgentRuntime. It is not a grant or persisted ownership record; outer lifecycle must acquire/validate it and owns checkpoint/cleanup. Request run mismatch is denied before host directory/session creation.

Authenticated RunBody may contain a trusted ready lease combining BrokerLease and ExecutionBinding. Broker mode requires runId equality and both client validators; API receipt is returned on the final result as revisionReceipt. Endpoint origins come from process configuration, never request-supplied routing. No database schema changes.

RuntimeClient leased calls carry explicit repository/owner alongside ExecutionLease internally; these are never sent as runtime-selected authority. Terminal NDJSON revisionReceipt must equal the persisted owner-scoped Receipt, with closed/confirmed/succeeded status and matching workspace/broker/grant. No schema changes.

Workspace identity creation: the repository may insert revision_workspaces for a committed owner-scoped project/heat after migration. It preserves the v1 defaults (null head/active attempt, generation zero), enforces heat membership through races and reuses existing identity under a write transaction. This is not a revision or acceptance record.

ImportedWorkspace is a trusted offline operation result containing workspace_id, revision_id and verified Artifact metadata. It adds no schema or acceptance status. The artifact becomes durable before root registration; a failure between these steps can retain unreferenced bytes without changing the workspace head.
