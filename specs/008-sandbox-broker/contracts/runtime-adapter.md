# Bound runtime adapter

The TypeScript broker adapter receives one immutable ready lease from trusted orchestration: run ID, workspace ID, internal attempt ID, signed grant and deadline, plus a configured broker origin. It holds no administrative credential or signing key. create checks requested run/workspace binding and queries authenticated broker status before returning the attempt ID. If status acquisition fails it attempts independent release of the pre-provisioned worker; the generic withSandbox contract does not release failed acquisitions. It never provisions or chooses a seed. One adapter instance owns one lease; release permanently closes it to new file calls. Control-plane orchestration/production selection is still a separate gate.

GET /v1/attempts/{id} verifies the current grant, ready state and inspected running worker under lifecycle serialization. POST /v1/attempts/{id}/release authenticates the signed grant and atomically revokes only the exact immutable attempt before serialized confirmed cleanup. Same scoped release may confirm an already terminated attempt despite its revocation tombstone; it never authorizes new effects or higher-fence attempts. An expired grant cannot use runtime routes, including release: independent TTL/reconciliation and administrative cleanup remain authoritative, and runtime reports unconfirmed release instead of success.

File requests get a fresh random operation ID per adapter invocation (Pi Edit can issue multiple operations under one tool call). No automatic network retry, local fallback or shell execution. Caller cancellation/timeout can leave an effect unknown; close the adapter to new calls and require destroy/cleanup. Known application failures such as CAS conflict reject with safe stable codes without retiring a healthy lease. Return shape/correlation and size are checked; existing workspace wrappers additionally check hashes and operation-specific integrity.

Origins must be HTTPS or literal loopback HTTP, without userinfo/path/query/fragment; redirects are refused. Requests and response streaming share a bounded timeout; responses are size-bounded and errors do not echo URLs, grants or response bodies. destroy uses its own bounded request, independent of an already aborted tool signal, and succeeds only on matching confirmed terminated response. Repeated successful destroy is idempotent; failed release can be retried with the same grant while valid. No claim that HTTP transport success registers an output revision.

Acceptance requires actual Node adapter → loopback service → Docker → Pi file tools and confirmed release, plus bounded malformed/redirect/timeout tests. Production grant issuance/seed orchestration, checkpoint registration, cancellation under all faults and production selection remain open until separately verified.

Completion authority prerequisite: trusted preparation issues two purpose-separated bearer capabilities over the same immutable scope. Sandbox grants keep aud=atom-sandbox and typ=atom-sandbox+jwt; completion grants use aud=atom-execution and typ=atom-execution+jwt. Both use fixed HS256, exact claim/header schemas and strict trusted-time checks. The completion codec is explicitly supplied to the coordinator with its own configured key; no secret/key fallback. Both tokens are excluded from lease repr. Cross-purpose tokens must fail even with the same test key. This implements lease issuance only: the completion HTTP boundary must additionally compare every persisted binding, current owner and fence before acting. A completion token is neither administrative broker authority nor proof of product acceptance. Runtime delivery/endpoint integration remains open.

Completion HTTP contract: a mountable ASGI application provides POST /v1/executions/complete and /v1/executions/cancel with no request body or query. Require exactly one Bearer execution-purpose token, then compare its owner/project/run/API-attempt/grant/generation/base/issued-at/deadline against the migrated ledger and require an existing broker binding. Neither caller-supplied destination nor sandbox/admin credential can select execution. Every coordinator mutation keeps its own transactional checks. Return only confirmed closed result and optional receipt, with no-store; closed retries are allowed only with valid current ownership/token. Authentication precedes body read; no compression, bounded empty-body intake and bounded response sending. Errors are redacted, and unavailable/unknown work is never a success response. This boundary has no automatic schema/startup/production mounting.

Node completion transport: ExecutionClient receives explicit execution/workspace/broker-attempt/grant IDs, completion token and deadline plus an HTTPS or literal-loopback HTTP origin. It sends empty POST complete/cancel requests with no redirects, enforces one whole-response timeout (default 120 seconds, configured 1..300000 ms) and a 16-KiB uncompressed JSON cap. Every terminal identity/state/deadline/receipt field is validated. complete returns a receipt only for succeeded/closed/confirmed with an exact-scope valid receipt; cancelled/failed/timed_out responses cannot become success. cancel preserves the observed terminal outcome. No automatic retry, admin credential or local fallback. This transport is not yet the production runtime lifecycle hook.
