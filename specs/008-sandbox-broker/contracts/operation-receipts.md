# File operation ownership and receipts

Registry schema v3 adds operations keyed by (attempt_id, operation_id), storing canonical request hash, admitted attempt version, running/completed/unknown state, reserved/actual response bytes, bounded result JSON and timestamps. It stores no raw grant or write request. Read response caching does contain workspace data and requires the same protected host storage as snapshots. Exact v1/v2 schemas migrate transactionally preserving all prior tables/identity; unknown schemas remain rejected. No destructive downgrade or automatic receipt deletion.

Lifecycle file_operation accepts an already verified Grant, target registry attempt ID, logical operation ID and validated structured request. Acquire the existing control lock; require current unrevoked/unexpired head in ready state and exact target ID; persist running receipt before helper invocation. The fingerprint includes the tool call ID and operation, not an attacker-selected hash. Reusing an ID with changed input conflicts before effects. Completed identical requests return the original outcome only after fresh authorization. A preexisting running/unknown receipt is never executed again: retire/revoke the attempt and expose uncertainty.

One attempt permits at most 1024 receipts and 64 MiB retained/reserved response bytes. Reserve 12 MiB for read_bytes, 2 MiB for text/search and 4 KiB for write before effects; unused reservation is released on completion. Receipt capacity denial is not partial file success. Responses are bounded/encoded before a short transaction; completion rechecks current grant/head/ready state and the admitted version. Revocation/termination marks running receipts unknown in the same transaction as termination intent, so late output cannot become accepted completion.

Known read-helper failures and a write's explicit file_conflict may be recorded as completed error outcomes; repeated requests reproduce that error. Other write failures, transport errors, failed completion persistence, or changed authorization after effects are uncertain: persist revocation/unknown where possible, terminate the owned worker, and reject success. If registry is unavailable, lower readiness, still attempt direct owned-container termination, and leave the prior running receipt for restart reconciliation. No automatic write replay and no success based solely on an in-memory flag.

Cancellation persists revocation before waiting for the lifecycle lock. The helper's independent ten-second deadline bounds current work; the caller may receive busy while cleanup is pending. This is eventual confirmed cancellation, not instantaneous interruption or exactly-once distributed execution. Startup retires prior attempts and marks pending operations unknown. Checkpoint quiescing/HTTP scoped admission/runtime transport/seed import remain integration gates; successful operation receipt is not accepted revision registration.

Tests: real SQLite migration/limits/conflicts; actual duplicate writes and altered-request refusal; real helper effect followed by lost confirmation; actual process death after write/before commit; concurrent cancellation while regex runs, durable unknown result and verified container removal. Invalid/expired/revoked/cross-attempt grants must cause zero helper effects. No mock filesystem or fabricated success evidence.
