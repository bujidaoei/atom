# Seed and scoped file HTTP

## Administrative checkpoint transfer
POST /v1/admin/checkpoints/export requires the independent admin Bearer credential and one X-Atom-Grant token before reading a strict 12-KiB JSON object containing only attempt_id. Check exact current scope before export. Return application/octet-stream and X-Atom-Attempt, X-Atom-Export-Version, X-Atom-Revision and X-Atom-Artifact-Key (exact archive SHA-256); Cache-Control is no-store. The shared transfer slot remains held through bounded response sending, not only serialization. Export leaves the attempt quiescing. A failed/partial response is not storage or registration acknowledgement; a valid current grant can repeat export.

POST /v1/admin/checkpoints/confirm requires admin credential, X-Atom-Grant and exactly one X-Atom-Attempt, X-Atom-Export-Version and X-Atom-Registered-Revision header. IDs/digests are lowercase hex, version a canonical positive signed-64-bit decimal. Recheck matching current quiescing state or exact checkpointed replay before reading a five-second, MAX_ARCHIVE_BYTES application/octet-stream body containing the exported archive. Revalidate bytes and authority in lifecycle before confirmation. Return attempt_id/state/version/revision. Invalid header/body/auth/scope cannot advance state. The v1 protocol deliberately sends the bounded archive back for verification; it is private-loopback transport, not a WAN-throughput claim.

Registered revision is an assertion from the authenticated trusted control plane, which must first obtain a real durable API receipt. Broker HTTP does not independently query the API database and runtime bearer grants cannot call these administrative routes. Confirmation never releases the worker. Revocation bypasses transfer admission and invalidates late confirmation. Source delivery is bounded to ten seconds; disconnect/cancellation releases the transfer slot. Production control-plane client/orchestration remain open.

POST /v1/admin/seed requires the existing administrative Bearer credential plus exactly one X-Atom-Grant signed token. Verify both before reading input. Only an already admitted provisioning grant may receive application/octet-stream, with no content encoding, at most 65 MiB + 14 bytes and a five-second read deadline. Lifecycle rechecks ownership after intake and after import; return attempt_id/state/deadline only after durable ready. Invalid or interrupted intake has no helper effects and may be retried while still provisioning.

POST /v1/attempts/{attempt_id}/files requires exactly one Authorization: Bearer signed grant; an administrative token is not a grant. Check current ready ownership and exact internal attempt ID before intake, then again in lifecycle. JSON exact envelope: operation_id, tool_call_id, operation. Maximum 50 MiB and five-second intake deadline; reject duplicate keys, nonfinite values, invalid tool/operation identifiers and operation schema before dispatch. Success returns tool_call_id and outcome {ok:true,data} or {ok:false,error}, preserving known helper failure codes. HTTP 200 does not imply a write succeeded: clients must inspect outcome.ok. Unknown effects use redacted 503 and retire the worker, not automatic replay.

One shared event-loop transfer lock admits a seed/file request at a time from intake through response serialization. Contention returns 503 before body intake, no unbounded waiter or collection of large bodies. Administrative revoke remains independent so cancellation persists during a transfer. This is a bounded single-process profile, not throughput/HA acceptance. Existing administrative JSON routes keep their 12-KiB bound. No compressed input; streamed actual size is authoritative regardless of Content-Length. Authentication, signature, schema and ownership failures must cause no request-induced container/file effects; maintenance is independent. Service errors never disclose token, raw content or internal exception details.

These endpoints expose actual lifecycle implementations. Runtime adapter, control-plane grant issuance/seed selection, output registration and production switching remain required. Network disconnect does not prove an already-dispatched helper stopped; durable operation IDs and lifecycle cleanup govern uncertainty.

Runtime acquisition/release endpoints are defined in runtime-adapter.md: authenticated GET /v1/attempts/{id} checks ready/live ownership; POST /v1/attempts/{id}/release persists scoped termination intent before serialized confirmed cleanup. Release has no body or transfer-gate dependency. Repeat cleanup may use its revoked but still-unexpired signed grant only for the exact immutable attempt; it cannot authorize file calls or affect successors. Expired tokens require existing administrative/TTL reconciliation.

Checkpoint recovery observation: POST /v1/admin/checkpoints/status requires admin Bearer plus X-Atom-Grant, then the same strict bounded JSON attempt_id and shared transfer admission. It returns exactly attempt_id/state/version/revision for current quiescing or checkpointed scope; version is positive signed-64-bit, quiescing revision is null and checkpointed revision is SHA-256. Expiry, revocation, wrong grant/scope and other states are denied. This read performs no driver or registry mutation. The trusted client validates every field. A checkpointed digest only supports recovery when matched to an existing API receipt and verified stored bytes; it alone does not prove registration or termination.
