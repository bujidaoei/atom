# Revision schema migration v1

Explicit offline-administration migration only; API startup must not silently modify an existing database. Recognize the exact current demo schema fingerprint at user_version=0, or exact version-1 extension schema and migration journal. Unknown/drifted schemas fail before backup or DDL. No production database is selected automatically.

Acquire BEGIN IMMEDIATE with finite lock wait, revalidate, create an exclusive backup via a separate read-only connection and SQLite backup API while the write reservation prevents concurrent changes, verify integrity/foreign keys/schema, synchronize backup, then execute additive DDL/bootstrap/journal/user_version in one transaction. Never overwrite a backup path or use the source as destination. Interrupted/failed DDL rolls back; a completed backup is retained. Repeat successful migration validates and returns without another mutation. Backup/DDL work is an operator workflow; no external effects occur inside normal revision-commit transactions.

Version 1 introduces revision_workspaces (separate main/heat heads and generations), revision_artifacts (immutable verified-storage metadata), revision_attempts (project/workspace/run/generation/base/deadline/cancel/termination state), revision_records (immutable scoped parent/artifact/producer links), revision_receipts (idempotent commit identity), revision_outbox (durable registration event) and atom_schema_migrations. Composite foreign keys and scope triggers prevent cross-project/workspace/run-heat references. Initial workspace heads are null, generation zero, and no attempt, artifact or revision is invented from legacy status. Existing data and mutable workspace files are preserved.

The migration only creates the data constraints. It does not authorize callers, allocate executions, import legacy bytes, register artifacts/revisions, deliver outbox events, switch preview/runtime, or establish HA. Existing API does not invoke it yet. Production adoption requires verified backup/restore, tenant mapping, repository methods and lifecycle integration. Restoring an old backup requires stopping writers and reconciling external workers/artifacts; never reset user_version or delete newer records to make an old binary start.
