# Durable local snapshot artifacts

Before project revision registration, trusted control must durably store the verified export. The initial private-host implementation uses a dedicated owner-only Linux directory, not the mutable project workspace. Artifact identity is SHA-256 of exact archive bytes; semantic revision remains the canonical manifest digest. Different valid manifest encodings may have different artifact identities but the same revision. No runtime-selected destination, filenames, deletion or registration callback.

put validates the bounded ATOMSNAP1 payload before filesystem effects. Under a finite directory flock, write an exclusive private .stage-UUID file, fsync it, publish by no-overwrite hardlink to the byte-digest filename, remove staging and fsync the directory before acknowledging. Existing objects are reverified rather than replaced. read checks no-follow regular/one-link/private-owner metadata, bounded size, byte digest and complete snapshot semantics. Errors have stable codes without raw content or paths. Disk failure never returns stored success; publication may be uncertain and a same-byte retry can confirm it.

Startup and each put may recover abandoned stage files only under the exclusive lock, after validating their exact reserved names/type/link count/owner. The lock serializes all store users and is released on process death. Never delete completed digest objects or unknown entries. Recovery scan is bounded; object retention/quota and referenced-artifact GC must be designed before production adoption. Directory symlinks, shared permissions or unsupported platforms fail closed. The trusted parent hierarchy must be protected from substitution.

This is actual local durable storage, not encryption, object-store replication, HA or backup acceptance. No database revision head is updated here. SQLite migration, current run/attempt fencing, compare-and-swap revision pointers, output registration and server/runtime completion ordering remain T009/T010. A crash between object publication and database registration may leave an unreferenced immutable object; retaining it is safer than deleting potentially referenced work. Production retention/backup/migration gates stay open.

Tests must use real Linux filesystem fsync/link/locks and process death: exact put/read/dedup, concurrent publication, corrupt/unsafe objects, interrupted publication with stage recovery, and preservation of already stored objects. Simulated storage acknowledgments cannot establish acceptance.

Primary-source verification (2026-10-01): Linux man-pages fsync(2) states that file synchronization does not by itself persist the containing directory entry, so this store explicitly synchronizes both file and directory; link(2) specifies that an existing destination is not overwritten. flock(2) documents advisory descriptor-associated locks and platform/network-filesystem caveats. Deployment must use a validated local filesystem and cooperating store users; this implementation does not establish NFS/SMB or power-loss behavior. Sources: https://man7.org/linux/man-pages/man2/fsync.2.html ; https://man7.org/linux/man-pages/man2/link.2.html ; https://man7.org/linux/man-pages/man2/flock.2.html .
