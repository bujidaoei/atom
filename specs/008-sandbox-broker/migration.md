# Revision schema migration operations

Status: offline component implemented against disposable databases. Production adoption requires application repositories, workspace creation/deletion behavior, snapshot import, revision registration and runtime/preview integration. Do not run against the live demo yet. The separate broker database remains version 3; this document concerns API schema v1.

Administrator command from the backend environment: `python -m app.migrations DATABASE --backup BACKUP`, with explicit absolute source and new backup paths. No implicit configured-database lookup. The runner validates supported schema and integrity, reserves the writer, creates a SQLite backup including committed WAL, verifies and synchronizes it, then commits additive DDL, empty workspace heads and a journal together. Existing destinations are never overwritten. Success returns version, applied flag and backup digest; errors return stable codes without database contents. Repeated migration validates and returns the recorded digest without creating a backup.

Before eventual production adoption, stop API/runtime writers, reconcile workers, inventory database/workspace data, and retain a separately verified backup and restoration rehearsal. Paths require protected administrator-owned directories; concurrent administrator path replacement is outside this tool's boundary. Linux backup mode is 0600 and the parent directory is synchronized. Windows directory persistence is not asserted. Backup copying has a 30-second progress deadline and source lock acquisition is bounded; full integrity verification and digest scanning are offline work without an overall deadline.

Backup failure rolls back the source transaction but can leave an incomplete destination. Preserve it for diagnosis and retry with a new path. Existence is not validity: `app.migrations.verify_backup(Path(...))` verifies baseline schema, integrity and foreign keys and returns a digest. Interrupted DDL leaves a verified baseline backup and SQLite rolls back the incomplete transaction on recovery. Never reset user_version to bypass validation.

Rollback: keep writers stopped; preserve current database and journals/WAL for diagnosis; use SQLite's backup API to restore the verified baseline backup into a new database; verify expected business rows and schema before switching configuration. Do not copy only the main file of an active WAL database. Reconcile worker/artifact effects before restarting the old application. The restored database can be migrated again using a new backup path. Production cutover and external-effect rollback are not implemented or accepted by these tests.

Tests use real temporary SQLite databases for preservation, WAL, contention, drift rejection, exclusive backup, failed DDL, abrupt process exit, restore and referential constraints. The integration harness exercises Linux backup synchronization and crash/restore in an actual restricted container. Test fixtures are not production business data or physical power-loss acceptance.

Initial file import component: after stopping legacy API/runtime writers, trusted orchestration may call app.workspace_import.import_workspace(repository, store, owner=..., project_id=..., source=absolute_workspace, heat_id=...). Supply a verified private ArtifactStore and migrated repository. The source must be a quiescent Linux workspace, outside database/artifact storage; paths must come from trusted project mapping, never model/client input. Existing snapshot exclusions and safety limits apply. Exact repeat is idempotent; changed input conflicts instead of overwriting the root. Preserve unreferenced artifacts after failures for future audited retention. This internal function does not implement writer shutdown, full migration inventory, production cutover or preview switching; live migration is still prohibited pending those gates.

Broker-backed API startup now requires the already migrated database to be an owner-held regular file with one link and mode 0600 (no group/other permissions), and the artifact directory to exist privately. A Linux inode flock prevents cooperating API processes from serving the same database concurrently; failed startup releases ownership. Keep parent directories protected and do not replace the database while running. Main scheduling and preview adoption are still incomplete, so this component does not authorize live cutover.

Supported-version backup prerequisite: app.migrations.backup_database now acquires BEGIN IMMEDIATE before schema/integrity checks and creates an exclusive synchronized snapshot of baseline or v1. It returns BackupResult(version, sha256). verify_backup defaults to baseline for existing callers; v1 requires expected_version=1. Unsupported versions/booleans, drift and active writer contention fail closed. Real WAL/restore and Linux private-file tests pass. v2 schema/migration and production restoration remain unimplemented.

v2 offline extension is available only by explicit target_version=2 / --target-version 2. Baseline upgrades apply v1 then v2 within one transaction after one source backup; v1 upgrades retain the v1 journal row and add v2 with the v1 backup digest. Journal replacement is transactional and has no incoming foreign keys. Baseline fingerprint and v1 definition remain unchanged. Exact v2 schema/journal validation rejects drift, lower target rejects downgrade. Existing application startup remains v1-only. Adoption and full verification provenance migrations plus live cutover are unfinished; no production upgrade is authorized by component evidence.

Explicit --target-version 3 now supports baseline/v1/v2 source databases with verified source-version backup and transactional journal preservation. Content bindings start empty; legacy releases do not acquire invented routes. Schema drift checking includes exact v3 definition/hash. Existing runtime repositories remain v1/v2-only as previously scoped, so do not upgrade a serving application. Live migration, host binding repository and private capability integration remain open.

Explicit --target-version 4 supports offline baseline/v1/v2/v3 upgrade with a verified source-version backup and preserved journal chain. It creates empty console/content-access tables; existing JWTs are not converted into authenticated durable sessions. v1/v2/v3 source definitions are unchanged. Default target stays 1; serving runtime/release/content repositories have not been switched to v4. Restore the verified pre-upgrade backup with services stopped if rehearsal fails. Real Linux forced exit after v4 DDL recovers v3, then retry reaches v4 and versioned backup verifies. Do not apply to production before application auth/serving migration and rollback acceptance.

Internal release/verification/content repositories now explicitly accept verified v4, including atomic content binding on new v4 publication. This enables isolated service integration tests only; RevisionRepository/main broker runtime and console login selection are not migrated. v4 database cutover remains prohibited until complete application compatibility and rollback gates pass.

Explicit console selection now exists: ATOM_SESSION_MODE=durable, ATOM_CONSOLE_ORIGIN=<canonical HTTPS origin>, ATOM_COOKIE_SECURE=true, ATOM_COOKIE_PATH=/, after offline v4 migration. Startup checks the durable ledger before serving. Uses a new __Host-atom_console cookie and rejects all legacy credentials; users must log in again. Default remains legacy for the current unmigrated deployment. Main broker RevisionRepository still requires v1, so do not activate this combination in production or migrate a running database. Route tests are not combined runtime/schema rollout or rollback acceptance.

Current runtime compatibility update: RevisionRepository/main broker execution now accepts exact verified v1 or v4. Full-schema and journal checks remain at construction and transaction entry; intermediate v2/v3 remain offline-only runtime targets. The real production-mode application lifespan plus own Node runtime/broker matrix passes on v4 with durable auth enabled, resolving the earlier v1/v4 incompatibility. This is not permission to skip stopped-service backup, live-data migration rehearsal, trusted ingress/cookies and deployment rollback acceptance. No production database was changed.


### Audit v5 offline foundation

Migration creates empty audit and delivery tables without historical backfill or credentials. Current subprocess crash evidence is Windows local SQLite, not Linux host power-loss recovery.
