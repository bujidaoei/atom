# Decisions and basis
Use existing own runtime port, not a replacement agent loop. Source inspection shows its exec currently accepts arbitrary command text even though server exposes only file tools: migrate to structured file operations before claiming least privilege. Current tmpfs experiment proves export must precede stop; runtime ownership fix guarantees release attempt, not termination.

Use fixed HS256 and dedicated key for first trusted-host broker. PyJWT official API requires allowed algorithms configured independently of attacker headers: https://pyjwt.readthedocs.io/en/stable/api.html (consulted 2026-09-30). Strict schema/time checks add bounds beyond generic JWT validation. No signature algorithm negotiation. Shared-key broker is privileged/trusted; runtime holds only scoped bearer tokens. EdDSA/public verification would separate signing authority but adds key distribution/dependency operations; not necessary to claim an untrusted broker boundary because none is proposed.

Host-local durable registry is for owning this host's containers; it must not replace parent PostgreSQL execution/fencing design. A single broker plus durable restart is recovery, not HA. No final server capacity claim until actual designated host is inspected.

Registry implementation consults SQLite's transaction semantics (https://www.sqlite.org/lang_transaction.html) and application schema version mechanism (https://www.sqlite.org/pragma.html#pragma_user_version), 2026-09-30. BEGIN IMMEDIATE serializes competing writers or returns SQLITE_BUSY; finite timeout and rollback are required. Exact v1 schema is checked before use, rather than silently create_all/mutating unknown schemas. WAL/FULL settings are not substitute evidence for host power-loss recovery.

Standalone service uses FastAPI lifespan for resource acquisition and shutdown (official https://fastapi.tiangolo.com/advanced/events/, consulted 2026-09-30). Periodic task scheduling, fail-closed readiness and bounded streamed JSON are project decisions, tested separately; the framework does not provide durable container ownership. A Starlette requests documentation fetch failed; no claim relies on that failed fetch. Real installed-framework ASGI and loopback HTTP tests verify implemented behavior. Single-process loopback is the initial trusted-host scope, not HA or public TLS deployment acceptance.

File-operation design checked Python 3.12 os descriptor APIs (https://docs.python.org/3.12/library/os.html) and signal timers (https://docs.python.org/3.12/library/signal.html), 2026-09-30. Platform-specific O_NOFOLLOW/dir_fd semantics justify Linux-only helper execution; host Windows tests validate schemas and actual Linux containers validate file effects. Signal documentation is not assumed to guarantee interruptibility of arbitrary native extensions: the selected built-in regex/helper path is tested with a catastrophic expression and real one-second alarm. No arbitrary extensions/commands are exposed.

While enabling existing workspace tests, npm audit identified Vitest/@vitest/mocker <4.1.11 and the existing own-runtime Undici 8.10.0 dependency. Maintainer advisories consulted 2026-09-30: https://github.com/vitest-dev/vitest/security/advisories/GHSA-82fw-gwwq-j7x9 (patched 4.1.11) and https://github.com/nodejs/undici/security/advisories/GHSA-w293-vg96-wgc3 (patched 8.10.2). Pinned those patch versions, rather than forced major upgrades. Audit concerns package versions/available advisories, not proof of application exploitability or a complete audit of compiled gateway bundles. Pi's locked dependency declarations are not edited.

Release audit on e7c4bd3 and refreshed official Lovable publish/Replit rollback evidence are in contracts/revision-release.md. Schema/evidence identity must precede publication route migration.


Security audit research (2026-10-01): reviewed Cursor compliance/monitoring, GitHub enterprise streaming and GitLab audit streaming primary sources linked in contracts/security-audit.md. Verified separation of security audit from usage telemetry, metadata privacy boundary and duplicate-permitted export semantics. Current source has diagnostic logging but no durable audit table/outbox. Decision: transactional committed events plus separate export/observations, not logging-only acceptance. Vendor implementation internals and compliance certifications are not inferred. New schema/runtime compatibility and fault acceptance must precede enabling this design.


### Audit destination research — 2026-10-01
Reviewed official OWASP SSRF guidance (https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html): explicit destination allowlisting, redirect restrictions and DNS/IP validation are complementary controls. Python TLS documentation (https://docs.python.org/3/library/ssl.html) documents trusted certificate/hostname checks; ipaddress documentation (https://docs.python.org/3/library/ipaddress.html) distinguishes special/public ranges. HTTP client documentation (https://docs.python.org/3/library/http.client.html) distinguishes per-operation timeouts from whole-operation limits and warns debug output prints protocol data.
Atom decision: initial operator-configured export endpoints use a canonical host/path and1-8 explicit canonical public IP pins on443. Connect numeric IP directly with no DNS/proxy and preserve original host for certificate/SNI. Changing approved IPs or token keeps destination identity; changing host/path/scope creates a new identity. This is intentionally an operator-managed receiver contract; SaaS receiver IP changes need a reviewed configuration update. No dynamic DNS resolver, private receiver exception or arbitrary caller URL is introduced. Future HTTP delivery must disable redirects, avoid protocol debug logging, bound the entire operation and define durable receiver acknowledgement. Application IP classification does not replace production egress firewall/routing controls.


Audit HTTP parser research — 2026-10-01: h11 official API https://h11.readthedocs.io/en/latest/api.html documents its HTTP event/state model, NEED_DATA and protocol errors. Atom uses this existing public parser over the pinned TLS stream, declares h11 directly rather than relying on an httpx transitive dependency, and separately enforces total deadline/bytes/informational limits and application-specific ack. The digest-ack contract is Atom's own receiver protocol, not attributed to h11 or a vendor.


### Governance/retention research refresh — 2026-10-01
Official Atoms [history](https://help.atoms.dev/zh/articles/12129557-project-history) and [publishing](https://help.atoms.dev/en/articles/12129577-publish-your-project) reinforce separate source/target selection and code/data/external-action recovery verification. [GitHub streaming](https://docs.github.com/en/enterprise-cloud@latest/admin/monitoring-activity-in-your-enterprise/reviewing-audit-logs-for-your-enterprise/streaming-the-audit-log-for-your-enterprise) distinguishes finite continuity buffers and receiver acceptance limits from retained copies; [GitHub API](https://docs.github.com/en/enterprise-cloud@latest/admin/monitoring-activity-in-your-enterprise/reviewing-audit-logs-for-your-enterprise/using-the-audit-log-api-for-your-enterprise) uses different windows for ordinary audit versus Git events. [GitLab audit](https://docs.gitlab.com/user/compliance/audit_events/) documents indefinite retention, while [streaming](https://docs.gitlab.com/user/compliance/audit_event_streaming/) separates owner deactivate/delete and receiver dedup. These different policies justify explicit Atom policy/obligation modeling, not borrowing one vendor TTL.
Current code plus real SQLite tests prove configured-only status can omit retained old-destination backlog. New receiver acknowledgements cannot settle old receiver obligations. Decision: persistent destination registry and generation-fenced administrative transitions precede any retention/pruning implementation; preserve existing v1-v5 definitions. Detailed proposed contract: specs/008-sandbox-broker/contracts/audit-governance.md. Recovery-manifest product design extends existing evidence chain without implying a delivered UI. Direct atoms.dev/zh/my-projects web fetch returned Internal Error; this does not prove product downtime and provides no new authenticated/paid-flow evidence. No vendor audit-stream retry/retention behavior beyond documented sources is assumed.


## T033 archive/restore boundary research — 2026-10-01
- SQLite Online Backup API: https://www.sqlite.org/backup.html documents consistent backup snapshots and incremental copying with explicit error handling. For Atom, keep whole-database recovery on the existing checked backup API; a raw main-file copy is not acceptance evidence for current committed state.
- SQLite WAL: https://www.sqlite.org/wal.html explains that a long reader can stop checkpoint progress. Atom archive extraction must use bounded read transactions; filesystem/network work runs after releasing the source snapshot. Holding a read transaction across a remote transfer is rejected.
- Amazon S3 Object Lock: https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock.html makes retention and holds version-specific; a key can gain a newer version or delete marker while the original version remains protected. A hold and an expiry are independent controls. This is storage mechanism evidence, not selection of AWS or a legal policy for Atom.
- Amazon S3 integrity: https://docs.aws.amazon.com/AmazonS3/latest/userguide/checking-object-integrity-upload.html states that multipart and some encrypted-object ETags are not whole-object MD5 digests. Atom must record its own full-payload digest and exact object version/storage identity, then independently read/restore; an ETag or successful upload alone is insufficient.
Actual SQLite probes in test_audit_archive_boundaries.py demonstrate a schema-valid/integrity-valid raw main-file copy missing a committed audit event, versus existing backup_database plus fresh restore preserving exact event dictionaries and source session. A held reader delays checkpoint completion until rollback. Whole database backup contains authentication fields, so it cannot substitute for a scope-limited external audit archive. These findings refine T033 without claiming archive implementation.


2026-10-01 T034 official-source review: SQLite foreignkeys.html requires connection-level enforcement and constrains parent deletion with dependent children; autoinc.html distinguishes never-reused automatic IDs from consecutive IDs; lang_createtrigger.html describes persistent/TEMP trigger boundaries and RAISE. Local inspection confirms event AUTOINCREMENT, delivery-to-event FK, permanent delete guards and live-only max(sequence) reader upper. Design consequence and source links are recorded in contracts/audit-pruning.md; no prune behavior is claimed implemented.

T017.2c container decision, 2026-10-02: official Playwright Docker documentation warns its published image is intended for testing/development and does not recommend using it by default to visit untrusted pages; root disables the Chromium sandbox, while nonroot plus an appropriate seccomp profile is recommended (https://playwright.dev/python/docs/docker). Docker's none network driver creates loopback only (https://docs.docker.com/engine/network/drivers/none/), allowing a pinned origin and browser to share an isolated network namespace without external egress. The planned worker needs a pinned browser version, nonroot Chromium sandbox, read-only root filesystem, private bounded temporary memory, no Docker socket, network none and finite CPU/memory/PID/runtime caps. The official Playwright example's `--ipc=host` is a crash-avoidance suggestion, not an acceptable unreviewed isolation default; actual private shared-memory sizing and browser success must be measured. No container or release-authority claim follows from this research alone.

T017.2c2 measured boundary, 2026-10-02: the official image tag/digest is https://mcr.microsoft.com/zh-cn/artifact/mar/playwright/python/tag/v1.58.0-noble-amd64 and the project vendors the official v1.58.0 seccomp profile from https://github.com/microsoft/playwright/blob/v1.58.0/utils/docker/seccomp_profile.json (download SHA-256 `cc3e61cabda6bbc1e53e54d27ba4d55a9d3be829b6dd1a596f4a7b31b1cc7849`). Playwright's BrowserType API explicitly says `chromium_sandbox` defaults false (https://playwright.dev/python/docs/api/class-browsertype); the worker therefore sets true. An actual Docker Desktop Linux container passed a root-relative asset/DOM check with `--network none` and a private 256 MiB `/dev/shm`; a `/proc` probe observed a Chromium process in a different user namespace than its Python parent. Dropping every capability first failed at Chromium's `sys_chroot` zygote check; restoring only `SYS_CHROOT` passed. These measurements establish one local container configuration, not host-independent production isolation or trustworthy v13 result registration.

2026-10-02 rollback and content-site boundary refresh: Replit's current official [checkpoints and rollbacks](https://docs.replit.com/features/version-control/checkpoints-and-rollbacks) distinguishes code/project rollback from its optional development-database rollback and says production-database recovery is not automatic; its [development and production database](https://docs.replit.com/features/data-and-storage/development-and-production) guidance separates published data and deployment-preview checks. Atom therefore must label release rollback as an immutable static-artifact pointer transition only, with production data restore as a distinct recovery action. This is official product behavior evidence, not a claim that we operated a paid Replit account. The WHATWG [HTML site model](https://html.spec.whatwg.org/multipage/browsers.html#sites) excludes port from same-site calculation; MDN's [cookie scope](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie) identifies __Host- cookies as host-scoped rather than port-scoped. A second port on 159.75.231.98 is a different origin for DOM access but does not create a separate cookie/site boundary. Inference for Atom: IP-only console plus same-IP content on another port cannot satisfy the specified independent content-site boundary. An independent content site address and TLS deployment must be selected before public release; the user preference has been requested and production release remains gated.

## Commercial product comparison and Atom differentiation — 2026-10-02

Evidence level: official product documentation inspected; no authenticated vendor workspace, paid plan or live third-party project was operated in this pass. The direct `https://atoms.dev/zh/my-projects` page did not provide an authenticated workflow to inspect here. Treat UI paths, availability and plan-specific controls as documented behavior, not hands-on acceptance.

- [Atoms project overview](https://help.atoms.dev/zh/articles/12129555-overview), [publishing](https://help.atoms.dev/zh/articles/12129577-publish-your-project), and [history](https://help.atoms.dev/zh/articles/12129557-project-history) separate preview, live version and later updates; ask the owner to test visitor flows, desktop/mobile and live URL, and distinguish restoring a project version from reverting production data or external actions. Atom adopts that separation while requiring an immutable committed snapshot and separately verified browser evidence before promotion.
- [Lovable publishing](https://docs.lovable.dev/features/publish) deploys a snapshot, exposes audience choice and a quick security scan, keeps later draft changes off the live site, and supports republish/unpublish. Its documented critical-finding block can be enabled by workspace admins. Atom should make the selected audience and actual blocking evidence explicit in the release consent, then bind both to the same version-fenced release command; a generic green scan badge is insufficient authority.
- [Cursor Agent checkpoints](https://cursor.com/docs/agent/overview) provide an agent-session restore point separate from Git; [enterprise hardening](https://prod.cursor.com/docs/enterprise/security-hardening) centralizes model, privacy, repository and network controls. Atom should retain source Git history and versioned policy identity in the release proof chain, and later add organization-level policy administration; neither local checkpoints nor unrestricted model selection is a production governance substitute.
- [Replit version control](https://docs.replit.com/replit-workspace/workspace-features/version-control) combines Git with Agent checkpoints and a visual history; its [rollback guidance](https://docs.replit.com/features/version-control/checkpoints-and-rollbacks) distinguishes development checkpoint recovery from production database recovery. Atom's static release rollback must create a new immutable release with source and displaced pointers while keeping production data recovery as a separately approved, backed-up operation.
- [GitHub Copilot enterprise review](https://docs.github.com/en/copilot/how-tos/administer-copilot/manage-for-enterprise/manage-agents/enable-copilot-code-review) supports centrally controlled and automatic PR review; [cloud-agent risk controls](https://docs.github.com/en/enterprise-cloud%40latest/copilot/concepts/security-governance-and-network-settings/risks-and-mitigations) keep human review in the merge path. Atom's differentiator is a queryable evidence chain from requirement contract, exact revision and artifact bytes through isolated browser attestation, audience/policy decision, publication generation and audited rollback lineage. This is a design target, not a claim that Atom already provides the complete operator UI or organization governance.
- [v0/Vercel documentation](https://vercel.com/docs/v0) connects generated projects to deployment, environment variables and integrations. Atom's deployment model must likewise make environment-specific configuration explicit, but its current single-host production and missing independent content site do not yet meet that standard.
